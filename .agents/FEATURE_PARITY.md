# Feature parity

For agents, not people. `CLAUDE.md` says how to keep this current. Keep it terse.

- **Status:** `yes`, `partial`, `no`. A row that's different by design says so in its notes.
- **Paths:** desktop and web paths start at `packages/ui/src/`, and iOS paths at `apps/ios/Zuna/`, unless they're written out in full.
- **Web** shares the desktop's interface (`@zuna/ui`), so its rows follow the desktop's unless a note says otherwise. What only the web does is in "The web app" below.
- **Android** doesn't exist yet (`docs/ROADMAP.md`). Add a column when it does.
- **Last full check:** 2026-11-01, by reading and searching the code on Windows. Nothing was run for it, and Swift can't be built on that machine, so iOS `yes` means the code is there. `docs/IOS_PLAN.md`'s phase reports record what iOS was tested with on a Mac.
- **Web check:** 2026-11-01 on macOS 27, `apps/web/test/web-check.mjs` in Chromium and WebKit: signing up, the title's count, reading from the first unread message, sending with a link preview, a picture, a voice message, a reload, a second tab and "Use here", the narrow-window notice, the web's settings, and signing in again on a cleared browser. Firefox wasn't run: neither Playwright's nor Mozilla's Firefox starts on macOS 27 ("Could not find profile folder").

## Known gaps

Things one platform should have and doesn't.

- **iOS: no voice channels.** Text channels are there (rows below), and voice channels are listed with who's in them, but a tap only says they can't be joined yet (`Channels/ChannelList.swift`). The phone's device already takes part in their MLS groups, as `channels` is set in `apps/ios/core-bundle/src/entry.ts`. To build: `voiceAccess`, `voiceKey`, `setVoiceState` and the rest of the session's voice methods in `ZunaModels/CoreAPI.swift`, LiveKit's Swift SDK with per-participant keys from `voiceKey` and `voiceSenderKey`, and a call screen. Admins can't set a voice channel's audio quality, how many fit or screen sharing on iOS either (`Channels/ChannelEditor.swift` keeps them as they are).
- **iOS: no push for what's said to you in a channel.** The server sends none for channels (`server/internal/api/groups.go`), since only a device can tell what mentions someone, so the phone is only notified while the app runs (the core's `notify`). A push it could drop would need the Notification Service Extension's filtering entitlement (`com.apple.developer.usernotifications.filtering`) in `apps/ios/ZunaNotifications/`, or a silent push.
- **iOS: a channel's chat without the desktop's mouse bits.** No bar of actions on a message (a long press has them), no editing in place (edits go through the message box, as in iOS's other chats), no "Jump to present" bar (the round button), no member list beside the chat (it's in the channel's details), and no time on the left further down a run. These would go in `Channels/ChannelMessages.swift` and `Chat/ChatScreen.swift`.
- **macOS and Linux: the system's notifications, not the app's own.** Only Windows draws its own (row "Notifications" in "The desktop on each OS"), as asked. The others have no reply from the notification, no chat picture, and don't take a notification back when its chat is read or its message deleted. To add them: `startNotifications` in `apps/desktop/src/main/index.ts` and `drawsNotifications` in `apps/desktop/src/renderer/src/platform.ts`, and on Linux something for `notificationState`, which only asks Windows.
- **Windows: a window goes through Chromium, not natively.** Linux shares one through the portal (`--source window`). Windows needs `CreateForWindow` from the window's HWND (the number in Electron's `window:` id) in `apps/desktop/native/screenshare/src/capture/windows.rs`, a new encoder when the window changes size, as `encode_buffer` in `src/capture/linux.rs` opens one, and to end when it closes. Then `native` for windows in `zuna:display-sources` (`apps/desktop/src/main/index.ts`) and `windows` in `apps/desktop/src/renderer/src/platform.ts`. Nothing here could build for Windows.
- **Linux: push to talk under Wayland needs Zuna installed.** The global shortcuts portal only gives a shortcut to an app with an installed .desktop file named after its systemd scope, `zuna.desktop`, which the .deb installs and an AppImage doesn't, so there it's greyed out (`keyWatchSupport` in `apps/desktop/src/main/global-key.ts`). An AppImage could install its own into `~/.local/share/applications` on first run. Only checked on KDE: GNOME and Hyprland have the portal too, unchecked, and one that never says the key went up would leave it held.
- **Linux: a native window only run with KWin.** GNOME, wlroots compositors and Hyprland unchecked. One that keeps a window's stream at one size and marks the window with `SPA_META_VideoCrop` would need that read in `src/capture/linux.rs`, which doesn't ask for it.
- **Linux: VA-API's smaller picture hasn't run.** NVENC's, the OpenGL blit in `native/dmabuf_cuda.c`, has, from the app on KDE with an RTX 5080. VA-API's `scale_vaapi` in `native/encoder.c` was only compiled with `ZUNA_CHECK_VAAPI` on Windows. Should it fail, the share goes through the browser, so a limit on size still holds. `--check-dmabuf` only checks the same size. NVENC or AMF from CPU memory can't do it at all (`Encoder::open` in `src/encoder.rs`), which also ends up in the browser.
- **One app's sound with a share: unrun on Windows, missing on macOS.** Windows: process loopback in the native program (`apps/desktop/native/screenshare/src/sound/windows.rs`), with the app list from audio sessions and a window's app from its process; type-checked against Rust's Windows target without LiveKit, never built or run, and Windows 10 2004 or later. Everything but Zuna stays with Chromium there. macOS has Chromium's sound, unchecked, and no choice of app: that needs a ScreenCaptureKit program (an `SCContentFilter` of the app, `capturesAudio`) and `shareSound` set in `apps/desktop/src/renderer/src/platform.ts`. The web can't: browsers only offer a tab's sound or the whole system's. Linux on Wayland: the portal doesn't say whose a window is, on any compositor, so a window starts without sound and the picker says to choose its app (`useShareSound` in `features/voice/ScreenPicker.tsx`).
- **Hiding the pointer: native only, and not looked at on Windows.** Chromium takes `cursor: "never"` and goes on showing it (measured in `voice-check.mjs` on Windows), so the setting is only offered natively (`features/voice/ScreenSettings.tsx`). Web has no way to hide it. Natively it asks Windows and the portal. Through KDE's portal a received frame showed the pointer gone. On Windows nobody has checked a picture for it: compare a capture with and without `--no-cursor` with the pointer over something still.
- **Web, Firefox: unchecked.** Nothing has been run in Firefox yet (see "Web check" above). Its `MediaRecorder` may only record WebM with Opus, which the iPhone app can't play (`apps/ios/Zuna/Chat/Voice.swift` plays AAC in MP4). `web-check.mjs` reports what each browser records and whether Apple's decoder reads it.
- **Linux desktop: voice messages are Opus in MP4, unchecked on the iPhone.** Chromium has no AAC encoder on Linux, for `MediaRecorder` or WebCodecs (Electron 45, Chromium 156), so `lib/voice.ts` gets Opus in MP4, sent as `audio/mp4`. The iPhone app plays with `AVAudioPlayer` (`Chat/Voice.swift`). Apple's players are reported to read Opus in MP4 from iOS 17, but nobody has played one there. To check: `afinfo` on a Mac, on the `desktop-voice.m4a` that `ui-check.mjs` saves on Linux. If it doesn't play: a software AAC encoder in `lib/voice.ts`, or decoding Opus in `Chat/Voice.swift`. The web in Chromium on Linux records the same (`web-check.mjs`, Playwright's Chromium).

## One platform, by design

These aren't gaps, so don't port them without being asked.

- **Desktop only:** tray, title bar, automatic updates, system notifications and the unread badge, and Electron's fuses.
- **Desktop and web:** the resizable sidebar, and the content security policy (sent by `zuna-web` on the web).
- **Desktop and web:** mouse gestures in a chat: dragging across messages to pick them, and a double click to reply. iOS keeps tapping to pick and swiping to reply, as asked.
- **Desktop only:** native screen capture, and push to talk from another window.
- **Web only:** one tab at a time with "Use here", the unread count in the tab's title, the "Zuna was updated" reload prompt, and the "Make the window bigger" notice below 860 × 540.
- **iOS only:** App lock with Face ID or passcode, the cover in the app switcher, the iPad split layout.
