# Security details

How each of Zuna's protections works, for anyone checking them. [SECURITY.md](../SECURITY.md) says what they mean for the people using Zuna, what the server can and can't see, and the limits.

## Group encryption: MLS

Every conversation, including DMs, is an [MLS](https://www.rfc-editor.org/rfc/rfc9420.html) group, using the ciphersuite `MLS_128_MLKEM768X25519_CHACHA20POLY1305_SHA384_MLDSA44` (0x0052) of [draft-ietf-mls-pq-ciphersuites](https://datatracker.ietf.org/doc/draft-ietf-mls-pq-ciphersuites/). The implementation is [OpenMLS](https://github.com/openmls/openmls), compiled to WebAssembly, and natively for the desktop app and iOS.

Keys are agreed with X-Wing, ML-KEM-768 and X25519 together, so that welcomes, the tree's path secrets and external joins, which the server sees and keeps, can't be opened by whoever records them and later has a quantum computer: breaking them takes breaking both. The suite's signature scheme is ML-DSA-44 by the draft's code point, and in Zuna it means a device's hybrid key, Ed25519 and ML-DSA-44 together (below), which Zuna's crypto provider signs and checks for OpenMLS (`crypto/src/mls.rs`). So every leaf, key package, commit and group info takes forging both, and one signed with either alone, as a plain OpenMLS would sign it, isn't taken. It's the only suite the apps take, and the server refuses a key package, welcome or group info of any other. Zuna only talks to itself, so a code point is a label in its own data; one the draft gives another meaning later needs groups started again ([POST_QUANTUM.md](POST_QUANTUM.md)).

Each device is its own member of each group. Keys change at every membership change and at least weekly on active conversations. The server's only role in MLS is enforcing one order of commits per group.

## Message content

Each MLS epoch exports a content key (RFC 9420 section 8.5). Messages are encrypted under it with XChaCha20-Poly1305, padded to 256-byte blocks, and signed with the sender's device key, Ed25519 and ML-DSA-44 together. The signature matters because all members share the content key: without it, any member could impersonate another. What's signed says who wrote it as well as what it says, so a server can't put one person's words under another's name, even with a member's help. Reactions, read positions, pins, deletions and typing signals are signed the same way, and say which message or person they're about. Every signature also names the account and device it's from, so a device key that someone else's certificate names too can't pass one person's reaction off as another's.

Who signed, and the signature, are inside the encryption: an envelope is `nonce || XChaCha20-Poly1305(content key, aad, pad(version || user || device || signature || body))`, where the authenticated data names what it is, the group, the message or person it's about, and the epoch. A signature outside, over the ciphertext, would let the server try each member's device key on it to find whose it is. The version is 4, and the signature a device's hybrid one, 2,485 bytes. What's signed is `zuna/envelope-sig/v4|user|device|`, the SHA-256 of the authenticated data, a commitment to the content key (`HKDF(content key, "zuna/envelope-commit/v1")`) and the SHA-256 of the body. The commitment keeps what signing the ciphertext gave: a good signature proves its signer used this very key, which a key from a history grant proves itself by, so a member who opens someone's signed body can't seal it again under a key of their own choosing.

An app opens an envelope, reads whose device it says signed it, and checks the signature with that device's key, so it learns who wrote a message from the message alone, never from the server. One that names a device it doesn't know yet is held, out of sight, until it does. One that doesn't open under a key that has proved itself, or that nobody it names signed, is nobody's: it's kept without being shown, counted or notified about, and never as from whoever it names, so no member can frame another.

## Sealed sender

What a member adds to a conversation tells the server nothing of who sent it: messages, edits, reactions and taking them back, pins and unpins, an author's own deletions, and typing. Nothing the server keeps about any of these says who.

- **No session.** A sealed request carries no session token, cookie or device key. The desktop app, the iPhone app and `zuna-bot` send them on connections of their own, with TLS sessions of their own; a browser decides for itself which connection a request takes, so the web app only leaves its credentials out.
- **The send key.** Each epoch has one, `MLS-Exporter("zuna/send/v1", epoch, 32)`, an Ed25519 seed every member of the epoch can make, and nobody else. Whoever makes an epoch gives the server its public half with the commit, and a sealed request is signed with it over its method, path, time, epoch, token and body, so the server checks it against the one key it holds for the group and can't tell one member's signature from another's. Only the current epoch's key is taken, so someone removed can't write. A device that goes without a commit, as its person leaves, is banned or deletes their account, or as it's signed out, is still in the tree and would make the key until a commit took it out, so the server forgets the group's key as it goes, and takes nothing sealed for the group until a member's commit gives it the next epoch's, which apps send before anything else. The secret is never stored or handed on, and holding old content keys gives no way to make it. Every member checks the server's key against its own when it applies a commit or reads the group, and one that differs, from whoever made the epoch or the server, is put right by a member's commit, as every commit carries one. Undoing commits restores the key with the group info it went with.
- **Tokens.** A limit on a person needs a name, and a limit on a whole group would let one member use it up for everyone, so each sealed request that changes something spends a token: RFC 9497's verifiable oblivious PRF, suite ristretto255-SHA512. A device asks for them while signed in, a hundred small and ten large at a time, a random while after it runs low, never because something is about to go, and the server counts them against that person: a thousand small and a hundred large in six hours across their devices, ten times that for a bot. A small token pays for up to 32 KiB, a large one for anything up to the 256 KiB limit. The server evaluates them blind, under a key of its own for each size and six-hour period, and proves it used the key a request with no session is shown; a token redeems in its own period and the next. Redeeming one shows the server a token it issued and hasn't seen before, and nothing of whose it was. It's spent in the same transaction as the write, so one refused costs nothing. What changes nothing, a message sent again, a reaction added again or a deletion of what's deleted, spends none, and is sent on to nobody, so that it can't be used to have the server send a message to a whole group over and over. Each signed message also carries a short hash of the token keys its sender was shown, and an app whose own differ for the same period warns, as a key made for one person would let the server follow their tokens. Typing spends none: it's kept nowhere, and a limit by group and address holds it.
- **Item keys.** Changing or deleting something takes a key only its author's devices can make: `HKDF(subkey(account key, "author"), "zuna/item-key/v1|kind|group|item")`, an Ed25519 seed. A message or reaction goes up with its public half, which the server keeps beside it, and checks an edit, deletion or reaction taken back against. Item keys can't be told apart or tied to anyone without the account key, so they name nobody. After the account's keys are replaced, a device tries each key it holds, the older ones included. A reaction taken back keeps its ID on the server, without what it carried, as a deleted message does: every member was sent what its author signed, and could otherwise send it again under the same ID with an item key of their own. This only stands in for the server's own check: what apps trust is still the signature inside.
- **Files.** A file a message will carry is made with a secret, whose SHA-256 the server keeps, and the secret travels inside the message with the file's key. A sealed message shows each of its files' secrets, which the server checks, and from then on the file belongs to nobody. Forwarding shows the same secret. Uploading is named, and what each person may upload is counted over thirty days in whole MiB, so no total gives one file's size away. That count is kept by the day, so a copy of the server's data says who uploaded on which day, and on a day only one person did, whose the files made that day were.
- **What a sender's phones aren't told.** The server can't leave the sender's phones out of a push, so every notification waits about a second and a half, and the device that sent the message reads it at once, at its own message, which cancels the push for that person's phones as anyone's read would.
- **Slow mode and reactions.** The server can't hold a person it can't see to a pace, so each app holds its own person to a channel's slow mode, and hides a message from anyone else that came sooner after its author's last than the channel allows, less two seconds for the network, by the server's times. The most reactions one person puts on a message, 32, are held the same way. Tokens bound how much a modified app can send past either.
- **What one thing added makes everyone carry.** A reaction added or taken back goes to members on its own, with its message's new place in the change feed, never with the message and all its others (`ApiReactionChange`), and a message changed in any other way goes out live without its reactions: each app keeps the ones it has opened, with whose each is, and only a device that's behind fetches the full set, once. A reaction is held to 4 KiB, which a real one, under 3 KiB with its signature, fits, and a message's reactions to 1,024 and 1 MiB in all. Past the first hundred on a message, each takes a large token. A reaction that opens for nobody, under a key MLS gave, is one only whoever added it could take back, so a group's admin's app, and a channel's, has the server drop it by name, as it would delete someone else's message.
- **Someone added without the history** isn't told anything about what came before they joined, live or otherwise: changes to an earlier message go only to members who could fetch it, and a sealed reaction or pin, as the route can't tell who's asking, is answered with what changed, never the message.
- **What stays named.** A group admin deleting someone else's message, which needs their role; commits, and undoing them; a group's details; read positions; files being uploaded and fetched; voice and calls; reports. Each is about someone being somewhere, or something the server has to check.

A server that sets out to can often still work a sender out, from addresses, timing and who it didn't have to wake, as [SECURITY.md](../SECURITY.md#limits) lists. The promise is about what the server is told and keeps.

Using exported keys rather than MLS's per-message ratchet is a deliberate trade-off, and it's what makes history on new devices possible:

- **Gained:** a device you add later can read your past messages, and new group members can receive history if an admin allows it.
- **Given up:** forward secrecy within an epoch and, for stored history, against theft of your account key. See "Limits" in [SECURITY.md](../SECURITY.md#limits).

## Keys on new devices

Your **account key** is random. It encrypts your identity keys and a vault of content keys, all stored on the server as ciphertext, each kind under a key derived from it for that alone. It's unlocked by either:

- your **password**, stretched on your device with Argon2id (64 MiB, 3 iterations), or
- your **recovery key**, 200 random bits shown once at sign-up.

Your password never leaves your device. A key derived from it authenticates you, and a separate one opens a key pair that the account key is sealed to, with HPKE (RFC 9180) over X-Wing, ML-KEM-768 and X25519 together, as each device's own seal key and history grants are, so a copy of the server's data opens none of them for someone with a quantum computer, so any of your devices can seal a new account key to your password without knowing it. The first is bound to the server's address and your username, so one a malicious server collects is no use anywhere else, even if you use the same password on several servers. Clients only derive keys within fixed limits, so a malicious server can't downgrade them or make the app run out of memory.

Sealing to that key pair needs no secret, so a server could seal a key of its own to it. What you unlock also names the key your account began with, and signing in only goes ahead with keys that really are that account's. A device that already knows your account also won't give it up for one that began with another key.

## Hybrid signatures

Every key an app checks a signature with is two, made from one secret and checked together (`crypto/src/hybrid.rs`, and `server/internal/hybrid` for what the server checks): Ed25519, and ML-DSA (FIPS 204), which a quantum computer doesn't break as it would Ed25519. A key's first byte says which ML-DSA: a device's key, which signs everything it sends, is ML-DSA-44 (1,345 bytes, signatures of 2,485), and a lasting key, an identity key, a slot's signing key, a bot's setup key or the log's, is ML-DSA-65 (1,985 bytes, signatures of 3,374). A secret is that byte and a 32-byte seed, from which each algorithm's own seed is derived with HKDF-SHA-256 under a label of its own, so finding one of the two keys, as a quantum computer could Ed25519's, gives nothing of the other. Both sign the same input, `zuna/hybrid-sig/v1`, the kind, the SHA-256 of the whole public key, then the message, so neither half is a signature of the message on its own anywhere, and the hash ties each to its partner. A check needs both, Ed25519's strictly (no small-order keys or non-canonical signatures); ML-DSA's half is hedged, randomness going in with the message, as FIPS 204 recommends. Nothing an app checks takes Ed25519 alone. Rust's, Go's and Node's implementations are held to shared vectors, and ML-DSA's keys to NIST's own known answers.

Two keys stay Ed25519 alone, which only the server checks: the send key and item keys of sealed sending. Making them hybrid would add 2,420 bytes to every sealed request, and forging either takes a copy of the server's data, a quantum computer and an account, to do what the server always could: post what no app shows, or drop its copy of a message.

## Identity and devices

Each account has one long-term **identity key**, a lasting hybrid key. Each device's MLS credential is a certificate signed by it, naming the key that device signs with, a device's hybrid key. A certificate is bytes, as every leaf of every group carries one: its version, the account and device, the generation, the device's key, and the identity key's signature of all that (`createCertificate`), 4.8 KB. Certificates are public, so holding one proves nothing: clients check every member of every group, whenever a group's tree may have changed and before encrypting anything, against the identity key they know for that person, and that the member really signs with the key its certificate names. So without that identity key, the server can't add a device to anyone's account. Whoever tries is removed, and everyone is warned. A device also counts only if the server's log of keys names it, for that account, with that signing key and a certificate of that hash (below), so what the server shows one person it shows everyone, the account's own devices included. A leaf nobody can check yet counts for nothing, and nothing is encrypted to a group while one is on its roster. A server can make accounts of its own, as it can sign anyone up, but it can't get one into a conversation. A group's roster (below) says who its admins have let in, and anyone else in its tree is removed before anything more is encrypted. A direct message's two people are in its charter (below), and anyone else in its tree is removed. What you write to someone can't be sent to another conversation either: if the server names one this device knows as something else, nothing is sent.

A device signs in to the server with a session token. Removing a device, a group admin deleting someone else's message, deleting a conversation, leaving one, changing who's a group's admin, managing invites, writing to the vault, replacing the account's keys or anything that carries them to its devices, and anything an admin does also take a signature by the device's own key, so a token found on its own, such as in a proxy's log, can't do them.

Clients pin the identity key each account's entry in the log of keys names, never what the list of people shows, and share those pins, and what you've verified, with your other devices through your encrypted vault. One manifest there lists all of them with your preferences and how far along each person's chain of keys your devices have got, under a number that only goes up. It's one vault item, or for an account that has seen thousands of people several, each naming the manifest's number, how many parts it has and a hash of the whole, and a device takes it only once every part of one write is in, so leaving out a part leaves out the whole manifest. It's the only place any of that is kept, so the server can't leave out one person's pin or verification, and a device that has seen a manifest refuses an older one and says so. An account starts with one, and each replacement of your keys seals its number in, so a new device warns if it's shown an older manifest than that, or none. If two of your devices hold different keys for someone, they warn too. An account moves on from that key only by a signed chain that starts from it. Anything else, including two chains for the same person, produces a loud warning, including on a new device of yours.

## Replacing your account's keys

When a device is removed or signs out, your password or recovery key changes, or someone signs in with your recovery key, your app replaces your account key, identity key and HPKE key, in the background. It seals the new account key to each remaining device and to your password and recovery key, and publishes one signed link from the old identity key to the new one, listing the devices that stay. Contacts follow that chain, and from then on a certificate signed by the old identity key means nothing unless its device is on the list. The vault is sealed again under the new key. The design and what it can't do are in [ACCOUNT_KEY_ROTATION.md](ACCOUNT_KEY_ROTATION.md), and **no independent cryptographer has reviewed it yet.**

## The log of keys

Each server keeps one log of every change to who holds which keys: an account made, a device added or removed, a certificate or seal key replaced, a new generation of an account's keys, an account deleted. Each change appends an entry in the same database transaction as the change itself, so one is never kept without the other (`server/internal/store/log.go`). The design, and what it can't do, is in [KEY_TRANSPARENCY.md](KEY_TRANSPARENCY.md).

- **The tree.** Entries are hashed into a Merkle tree as RFC 6962 does: a leaf is `SHA-256(0x00 | record)`, a node `SHA-256(0x01 | left | right)`, split at the largest power of two below the size. The server signs a head, `zuna/log/head/v2|era|size|root`, with a lasting hybrid key it made once, Ed25519 and ML-DSA-65, which someone signed in is given by `GET /api/info`. A head carries no time, which would tell everyone when devices came and went.
- **Records and bodies.** A record is 80 bytes: a random nonce, a tag of the account's ID and the nonce, a tag of the username and the nonce on an account's first entry (16 random bytes on any other, so kinds can't be told apart), and a hash of the body with the nonce. Everyone gets every record. The body, JSON with hashes of certificates, enrollment proofs, seal keys and link payloads rather than the things themselves, goes only to those the account is there for, as everything else about an account does. A device holds each body to its record: it has to hash to it, name an ID its user tag fits, and for an account, a username its name tag fits.
- **Every device reads all of it.** The list of people already holds every account and device, so a device fetches the log from where it left off, appends each record to the tree's frontier, and compares the root with the signed head. There are no proofs to ask for, and nothing about anyone can be left out without the root coming out wrong. The log is read before the list of people, which is judged by it. A record that comes without its body is tested against every ID the device knows, its own first, and if it fits one, the device asks for that account's bodies, and says so if the server won't give them to someone the account is there for.
- **What counts.** A device counts only if the log names it for its account, with its signing key and a certificate of that hash. One the server lists and the log doesn't counts for nothing, and in a group's tree it's removed with a warning. One the log says is gone is gone, whatever the server lists. A link the log names has to be the one the server hands over, and one it names that the server keeps back is a generation the device knows it's missing: it asks again, and a leaf whose certificate comes from it waits rather than being removed. A device with no pin for someone takes it from their account entry. A second account entry for an ID, or one whose key isn't the pin, is the existing `changed` warning, and two links for one generation the existing fork warning. An account made under a username an earlier account still holds counts for nothing, and the name's holder is warned. What a device counted before still counts while the log can't be read, and only what's new waits.
- **Your own account.** The entries about this account get the checks a device makes of what the server says about itself, and now nothing can be kept from it. The question whether a new device that signed in was you is asked from the device's entry, so the server can't skip it, for every entry after this device's own, and kept until you answer, over everything else in the app (`getNewDevices`, `answerNewDevice`). No removes that device, which replaces the account's keys, and asks you to change the secret its enrollment proof shows it signed in with, the password or the recovery key, as whoever has it can sign in again until it changes; one the server keeps out of this device's list has nothing to remove, and goes when the keys are replaced without it. An answer stays on the device that gave it, as whoever signed in could give one too, so each device from before asks, and stops once that device is gone. The account's first key and username have to be its own, and each link one its devices made.
- **Heads compared.** A signed message carries its sender's newest head, beside the hash of the token keys, when it's newer than the last it carried to that conversation, or a week on. The account's vault manifest carries the log's key and a head, so its later devices take the key from there, not from the server, and refuse a log that doesn't hold that head. An invite link carries a hash of the key (`zuna/log/key/v1`), which is two kilobytes, and the inviter's head after the `#`, as `log=`, and the key the server gives whoever signs up has to have that hash, which whoever joins holds the log they're given to. A device given a head no bigger than its own checks that its root at that size is the same, and given a bigger one, reads the log that far first. Two roots for one size, both under the log key's signature, are proof that the server keeps two logs: the device keeps both heads and warns. A log shorter than a head someone holds is the server going back, which gets a warning too. A head signed by another key gets a milder warning, naming whose message it was in, as that's the one a member can cause.
- **Signing in.** A device signing in reads the log before it registers, with its own account's entries, and holds what it was handed to it: the generation and head link have to be the newest the log has for the account, so a server can't hand a new device an older generation the log shows was replaced.
- **Seal keys.** A device seals the account key to another of its devices only under the newest seal key the log has for it, so a server can't offer an older one again, even to a device that never saw the newer.
- **Eras.** A server restored from a backup has a shorter log than its members' devices have seen. Its owner runs `zuna-server --new-log-era` once, which writes the log again from its tables, under the next era and the same key. Devices take a newer era signed with the key they pinned, say so once, and read it from the start, holding it to the pins and chains they keep apart from it, so a key that changed across the reset is `changed` as it would be any other time.

A server can still give out a false key: the log makes the real owner's devices see it, or forces the server to keep two logs, which the first signed message between two people gives away. Someone kept apart from everyone from their first moment has nobody honest to compare heads with until they compare emoji with anyone at all. Nobody outside the server checks the log: the members' devices do.

## The emoji check

Pinning alone doesn't protect a first conversation: a malicious server could hand out a fake key from the start. The emoji check closes that gap. Two people compare 16 emoji (96 bits, from Argon2id over both whole identity keys, both halves of each, under `zuna/safety/v3`, at the same cost as a password). A server that swaps both people's keys only needs the two sides to agree, so a match is cheaper to find than for one fixed key: the memory Argon2id needs for every attempt, and the 96 bits, put that out of reach. If they match, each app holds the other person's real key, and since every device in a chat has to be signed by that key, nobody else's device can be in the chat as them. Saying they match only ever trusts the key those emoji were made from, so a server can't use that moment to swap in another. After someone's keys are replaced, the emoji change, and a verification only carries over if a device the other person has known for at least a week made the change. Otherwise that person goes back to unverified, and a line in your chat says so.

## Who's in a conversation

The server keeps a list of who's in each conversation, for what it does itself. A group also has a **roster**: who its admins are, and who they've let in, in a private extension of its MLS group context (`ROSTER_EXTENSION` in `crypto/src/mls.rs`, `packages/core/src/roster.ts`). MLS makes every member hold the same one, and only a commit changes it. Each version is signed by the device that made it and names the hash of the one before. Clients check every change before keeping it: an admin may change anything, anyone may take themselves off it, and when none of the admins is left in the group, the one person the server made its admin may take over and change nothing else. Whoever rejoins a group takes its roster only if it's the version held, the next one, or a later one an admin of the held version signed. Group admins are the roster's, for deletions, the group's details, history grants and who may add or remove people. The server's list of admins follows the roster, taken only from an admin's commit. What MLS proves is who actually holds the keys. Clients go by that, and by the roster:

- Someone the roster doesn't name, or a device that isn't what it claims, is removed before anything more is encrypted, and everyone gets a warning in the conversation.
- That someone left is only announced once their keys are really gone. Who removed them is named only if MLS shows it: otherwise, it would be the server's word.
- The member list shows a difference if there is one: someone who holds the keys but isn't listed, or who's listed with no device in the group.
- Only an admin's device can set a group's name and picture, which it signs, and an older copy can't be served again.
- A member can't remove someone from a group's keys: everyone is told, and the person removed rejoins straight away.
- A message under an epoch your device was in the group for only counts as sent by a device that was in the group's tree by then, and not after it left. One that isn't is marked unverified, so a member can't pass someone outside the group a key to write in it.

**What a conversation is** never comes from the server alone. A direct message and a channel have a **charter** where a group has its roster: what the conversation is and, for a direct message, its two people, signed by the device that started it, which for a direct message is one of them (`sealCharter` in `roster.ts`). It's written once and never changes, so a commit that changes it is refused. A device joining a conversation, by a Welcome or by itself, refuses one whose own state isn't what the device holds it as: a group's roster makes it a group, whatever the server calls it. A device takes what a conversation is from what your account's vault kept its keys under, when it holds any: each epoch key there is sealed together with what its conversation is, a group, a channel or a direct message with whom (`kindTag`), and a key is only used for a conversation of that kind. So a server that calls a group or a direct message a channel, which anyone on the server may come into, can't get a new device of yours to treat it as one and hand its keys over: the device goes by your vault, or failing that by the conversation's own state, says so, and only ever hands on keys for what everything it has says is a channel. Direct messages and channels started before charters have none, and for those your vault's record is what protects them.

## What the server can't make your app do

The server can say you're out of a conversation or signed out, but your messages stay on your device until you clear them, sign in again, or 30 days pass. It can say a message was deleted, too, but your app only erases its copy if the deletion was signed by the device of whoever wrote it or, in a group, of an admin. Otherwise the message is hidden as deleted and kept for 30 days. That includes a device you removed from your account in Settings, so a lost device isn't wiped if it comes back online: removing it cuts off its access, not what it already holds. Nor can it pin a message on its own: a pin only shows if a member's device signed it, and only a later pin or unpin, also signed, replaces one your app has seen.

## Deleting an account

Deleting an account takes its password, checked as a sign-in is and counted with the account's sign-in attempts, and a request signed by the device. The server takes the account out of every group, then erases its sign-in and recovery data and their salts, its sealed vault core and vault items, the slots and bundles that carry its account key, history grants, key packages, welcomes, sessions and push registrations, its profile and avatar, and revokes the invites it made. It frees the username, and the account's role becomes member. Its ID, identity key, chain of identity links, HPKE key and devices' certificates stay, with every device revoked: a device that comes later still checks what the account sent against them. Messages, reactions and files it sent stay on the server, which doesn't know which they are, and a direct message with it stays with it, as the server says who each one is between.

Other devices of the account are signed out, with `account_deleted` as the reason, and keep their data as after any sign-out. The device that asked erases its copy once the server agrees. Everyone else's apps take the account's devices out of the trees of their conversations, as after a ban, and show it as "Deleted account", with no picture, in place of what they knew of it.

The server could say an account was deleted when it wasn't. As with a ban, that only hides someone: their name and picture aren't shown, and they're taken out of conversations.

## Seeing what the server keeps

Settings, Your data, shows everything the server says it keeps that's tied to the account, and saves it as a JSON file. It's `POST /api/account/export`, which takes a request signed by one of the account's devices, so a session token alone, as one copied from a proxy's log would be, can't read it, and which only ever gives an account its own (`server/internal/store/export.go`). It's read in one snapshot: the account's record, its devices with their keys, sessions' times, waiting key packages and welcomes and push registrations, every conversation it's in, a direct message it's one of the two of, or one it has left where a change by it or about it is still kept, with who's in each (counted, for a channel), and how many messages there are, how big, and when the first and last were sent, its vault and history grants, files it still owns, what it uploaded each day, tokens it was given, invites, bots, channels and sounds it made, people it banned, its key replacements and how many entries the log of keys has about it.

What a copy would let someone guess the password from, or act with, is given only by its size: the sign-in and recovery checks and the slots sealed to the password and recovery key, the codes of invites, and the handles phones are woken through. The salt and settings the password is stretched with are given, as anyone asking to sign in is told them. Ciphertext kept in bulk is counted and sized, not sent. Reports about the account are left out, so that nobody can tell from it when they were reported. The core turns the answer into plain words for the apps (`packages/core/src/export.ts`), with what the server can read marked apart from what it can't, and what this device knows that the server doesn't, such as a group's name or a device's, shown as only on the person's devices.

It's what the server says it keeps. A server someone changed could keep more, or answer with less, and the page says so.

## Reporting someone

A report says whom and why: a user ID and one of a few reasons. It carries nothing of any message, which the server can't read, and the server stores it without who sent it. While it arrives, the server knows whose session sent it, and holds in memory, for a day, that this person reported that one, to refuse the same report again, and how many reports each person sent this hour. Neither is written anywhere. Whom an account reported is in its encrypted preferences, so that its apps don't offer to report them again. Admins see the reports, apart from those about themselves, which another admin or the owner has to look at. A ban, or the account being deleted, clears what it was reported for.

## Bots

A bot is an account, with an identity key, an account key and one device, as a person's has. A program runs it: `zuna-bot` (`apps/bot`), which holds the client core and does MLS for itself, on a machine its owner chose. So a bot is a member of each chat it's in and reads everything said there from the epoch it joined in, on that machine, and the server still reads none of it. [BOTS.md](BOTS.md) is the guide to making and running one.

**Setting one up.** The owner's app asks the server for a bot, which reserves its username and makes an invite that works once, for an hour, and only for that bot. The app makes a lasting hybrid key pair and builds the setup link: the invite, the community key, and in the link's fragment, which the server never sees, the 32-byte seed the pair comes from with the bot's ID, username and name, and its owner's ID and a hash of their identity key (`zuna/bot-owner/v1`). It keeps the public half, sealed with the rest of what the device stores. `zuna-bot init` signs up with that link: the bot's keys are made there, with 32 random bytes for a password nobody sees, so the server guessing passwords doesn't apply to a bot. It signs `zuna/bot-setup/v1`, its ID and its new identity key with the link's secret, and the server keeps the signature with the account and hands it out with the bot. The owner's device checks it against the public half it kept, and marks the bot verified, as comparing emoji would. A server that signed a bot up itself, with a key of its own, has no such signature to show, and the bot stays unverified. The bot's device pins its owner's identity key, the one the server lists for the owner as it signs up, only if it has the hash the link names, so nobody the server names later is taken for its owner.

**What a bot gets.** Nothing from before it was added: where a group shares its history, `addMembers` hands a person the older epochs' keys and a bot none, and the server refuses a history grant made out to a bot. Its profile, with its commands, is sealed with the community key and signed, as anyone's is. Only the bot can seal it, so its owner's app asks it to, in a message in their direct chat that only the owner's identity key is obeyed for.

**Who may add it, and where it goes.** The server refuses a commit that adds a bot unless its owner allowed whoever sends it: the owner, the server's admins for a listed bot set to that, or anyone. It hands out a bot's key packages only for a chat the bot may be in: to the person its direct chat is with, to someone who may add it to that group, or to a member of a group it's already in. The bot checks for itself when it finds it's in a group, by who added it, and leaves a group it shouldn't be in, so a server that lets someone through gains a member that goes. A bot can't start a group or a direct message, make invites or other bots, take a role on the server, or get a token for voice. A listed bot joins the channels the server says it was given, which is the server's word alone. A private bot's core joins none, whatever the server says.

**Who sees it.** The server leaves a private bot out of everything it tells anyone but the bot's owner and the people in a group with it: the list of users, profiles, key packages, the socket's frames and the bodies of its entries in the log of keys. Everyone gets the records, which say nothing by themselves, so a modified app can count records about nobody it can see, which says that private bots exist and that their keys changed, and can test guesses at a private bot's username offline against its first record. That hides it from people, other admins included, never from the server, which knows every bot, whose it is and which chats it's in. Its username is still taken, which someone asking for the same one is told, as of any name. A bot shows no presence: the server sends none for it, and the core shows none whatever arrives. In a chat, a bot is on the roster as anyone is, so nobody is in a chat with a bot without their app showing it, with its badge.

**Messages nobody is shown.** Two kinds of message carry a `signal` in place of something to read: an owner's changes to their bot, and the press of a button under a bot's message. They're sealed and ordered as any message is, so every member's device receives a press and can open it. The core keeps them out of every chat, shows no notification and stores nothing but that it saw them, and hands a press to the bot's own program. The sender marks them `silent`, which the server reads, to send no push for them, so the server knows which messages these are, though not what they say. Buttons are only shown under a bot's messages, and a link in one is opened as a message's link is.

**Where it runs.** `zuna-bot` keeps the bot's device key in a file only its user can read, as the Linux app does without a secret store, so whoever can read its data folder is the bot. Its API listens on `127.0.0.1` and takes a token from that folder. Its numbers for people, chats and messages are its own, kept in that folder, and mean nothing elsewhere. It fetches no file from an address and makes no link previews, either of which would tell a site where the bot runs.

## Profiles and the community key

Display names and avatars are encrypted under a **community key**, carried in the fragment of invite links (`#k=...`), with a key derived from it for profiles alone, as channels and sounds have theirs. Browsers don't send fragments to servers. Profiles are also signed by their owners.

If an admin turns on open sign-ups, there's no invite link to carry that key, so the app gives it to the server, and the settings screen says so. This exposes profiles, not messages.

## Servers without a domain

Given an IP address in place of a domain, the server makes its own certificate: a P-256 key made once and kept in its data folder as `certificate.key`, and a certificate from that key for each connection, as Chromium remembers its verdict on each certificate for a while. Its links carry the SHA-256 of the key's SubjectPublicKeyInfo, in base64url, in their fragment (`#pin=`), which browsers don't send to servers. The app keeps it with the account, sealed as the rest of it is, and before anything reaches the server, has its host trust that key for that address, and no other certificate for it: the desktop app's host through rustls (`apps/desktop/src/host/tls.rs`), and iOS through URLSession's and Network.framework's, and LiveKit's socket for voice, whose delegate, a private class of LiveKit's, the app gives the same check before a room first connects. The desktop app's LiveKit connection takes only the system's roots, so its voice can't reach LiveKit through such a server yet, and fails rather than trusting anything else. The key decides, not the certificate's dates or names.

- **Only an address over HTTPS can have a pin,** never a name. The core and both hosts check, so no link can have the app trust another key for a name, such as where updates come from.
- **A link can't change the pin of a server the device is on.** Anybody can send a link, and its key would be trusted as soon as it was pasted, before anyone decided to join. A new key needs signing out of the server and in again with its new address.
- **The first link decides.** Like the community key, the pin is only as good as the way the link came. A wrong one, with someone between the device and the server, lets them pose as the server, which E2EE already assumes a server may do.
- **A browser can't check a certificate by its key,** so the web app refuses such a server rather than trust whatever certificate the browser would.
- **Its key is P-256,** which a quantum computer could forge for whoever is between a device and the server, seeing what the server sees. It becomes ML-DSA once Go's TLS, rustls and iOS can check such a certificate, which none can yet; the link carries a hash of the key, so it won't grow. What the connection agrees on keys with is post-quantum already: the server offers X25519MLKEM768 first, as the desktop app and the iPhone app from iOS 26 do (`server/cmd/zuna-server/tls_test.go`).

## Channels

Everyone on a server can see and join its channels, so a channel is only as private as the server's membership. What they're called and everything said in them is end-to-end encrypted in the same way as a group's, and the server can't read any of it. The server does see each channel's rules: how many fit, how many may share a screen, whether the soundboard plays there, and its slow mode, which each app holds its own person to, but not admins, and hides a message from anyone else that came too soon (above).

To be in a channel, someone has to show they hold the community key, which comes with invite links and which the server doesn't have. Members check that for each person on the roster, and remove anyone who can't. A server can't get an account of its own making into a channel. Three things to know about that:

- **Open sign-ups** give the server the community key, so there it could.
- **Someone banned** still holds the key. The server takes them off the roster, and members remove them, but a server that wants them back could put them back. They'd get what's said from then on, not what was said while they were gone.
- **Old invite links** carry the key too. Whoever holds one can read channel names if they get hold of the server's data, and can sign up if the invite still works. Nothing else depends on that key.

A newcomer gets a channel's history from members' devices, which sign what they hand over. Any member can do that, since all of them may read all of it, so a member with bad intentions could hand someone a wrong key for an old epoch. That doesn't keep the right one out. Up to three members' devices answer each request, never the same one twice, and the newcomer keeps every key they hand on, with whose device signed it, until one opens a properly signed message: that one is kept, and whoever handed on another for the same epoch is named in a warning. The account's own copy, from its vault, takes the place of any granted key nothing has proved. The request stays open until a key opens something, and if what came opens nothing, the newcomer's app asks again, at most every six hours, and those who answered before don't answer it. Several members who all hand on wrong keys can still keep someone from a channel's history, never from what's said once they're in: only MLS's own keys are used for what's sent from then on.

## Voice channels

Media is encrypted in the app with a key from the channel's MLS group, frame by frame, before LiveKit sees it. LiveKit and the Zuna server can't hear or see it. The key exists only for the group's current epoch and is never stored or handed on, unlike the keys to messages: a stolen vault, or someone who joins later, can't open a recording of a call. A device in a room whose epoch has lasted six hours makes a new one, since the nonces frames are encrypted under start repeating after about thirteen hours of video.

- **What they do see.** The Zuna server sees who's in which voice channel, whether they say they're muted, deafened or sharing, and when. LiveKit sees who's in a room, by user and device ID with no names, and from when to when, who's sending what, how big it is, and how loud each person's audio is, since that's what lets it say who's speaking. Frames are encrypted, not hidden: their size and timing can say something about what's being said. It also sees each device's addresses, those on its local network too, in the candidates the app offers for media.
- **What LiveKit is told about a device.** The native app tells it neither the system nor the device's model, which LiveKit's Rust SDK would (`apps/desktop/patches/livekit-signaling.patch`). The iPhone app tells it iOS's version, the phone's model and the kind of network, as LiveKit's Swift SDK has no switch for them. A browser sends its `User-Agent`, which no page can take off, and which LiveKit reads the browser and system from. The Zuna server passes on no caller's address to LiveKit, and its own logs keep none (`server/internal/logs`).
- **What LiveKit keeps.** A LiveKit built by `deploy/`, through `update.sh` or the Docker image, is built from its source with Zuna's patch (`deploy/livekit/zuna.patch`), and keeps none of the above in its log, at any level, whatever its config says. Every field and message goes through one encoder, which lets through only keys on a list, with no room's or person's name among them, only plain values, and text with every address and every run of 32 hex digits, which is what Zuna's IDs are, taken out. LiveKit's own IDs, made up for each session, stay, so that one session's lines can be told from another's. One run by hand from LiveKit's own release writes the room's and each person's ID, every address a device offers and what it says it runs on. The patch also gives apps no outside STUN servers, where LiveKit would give each the address of Twilio's and Google's, which would each learn the address of every device that joins.
- **Against whom.** That's against what's kept by accident: a log that's later read, backed up, leaked or taken. It's not against a server's admin who sets out to learn these things, who can watch the network beside LiveKit, and no app can check which LiveKit a server runs. Against them only what the app doesn't send helps.
- **Who can hear.** Whoever is in the group. Someone removed goes on being able to open what's sent under the old key for about 1.5 seconds, while everyone moves to the new one. Someone in the room without the key can't open anything: the server can put someone in a room, but not in the group.
- **Who said it.** Everyone in the group can work out everyone's sender key, so a member could send media as another member. LiveKit can't. There are no per-frame signatures.
- **Against a quantum computer.** The room's key comes from MLS, whose keys are agreed with ML-KEM-768 and X25519 together, so what's recorded of a call can't be opened later by someone who records the group's commits too. The frame cryptor itself is AES-GCM under 128-bit keys derived from it: LiveKit's web SDK takes 256, but its native and Swift ones only 128, so all three stay at 128, which a quantum computer isn't known to break but leaves less margin than the 256 bits everything else has. WebRTC's own encryption to LiveKit, under the room's key, protects only what LiveKit sees anyway.
- **The microphone** is processed entirely on the device. Nothing about it leaves but what's sent.
- **Who can share a screen** is up to each server's admins, and LiveKit enforces it. Coming into a voice channel doesn't allow a screen at all, and the server only allows one after checking its rules, which it can also take back. See [SCREEN_SHARE.md](SCREEN_SHARE.md#what-a-server-says-and-what-a-device-chooses).
- **The iPhone's broadcast extension**, which records the screen before iOS 27, never has a key. It hands frames to the app over a socket in the App Group, which only Zuna's own app and extensions can open, and the app encrypts them. A broadcast started from Control Center goes out only once the server has made room for it, as one from the app's button does.
- **The native screen share** runs in the desktop app's own process and goes out from its own connection, under the device's own key, so its keys never leave the app. libwebrtc's logs stay off in the app unless `ZUNA_WEBRTC_LOG` is set, since the native frame cryptor has been reported to log keys. `apps/desktop/test/key-log-check.mjs` shares a screen with every log on and looks for that.
- **A screen shared in AV1**, an experiment that only the native app sends and opens, is encrypted whole by the same frame cryptor, which leaves no part of an AV1 frame out, and then goes out inside OBUs of its own, so that libwebrtc can packetize it: a metadata OBU holding the ciphertext, after, on a keyframe, a sequence header and a frame header with nothing of the picture in them, which say only that it's a keyframe, as RTP's own header does. The app takes the ciphertext back out before the cryptor opens it (`apps/desktop/patches/webrtc-sys.patch`). H.264 leaves its NAL headers out of the encryption, which say what kind each part of a frame is, so AV1 shows less. `apps/desktop/test/codec-check.mjs` checks that a watcher with another key opens nothing of either codec, and one with no encryption, as the media server is, nothing of AV1; of H.264 a decoder makes a few frames of what it can't open, from those headers.
- **The soundboard** is a server's sounds, which its admins add. Each one's name and the key to its file are sealed with the community key, as a channel's name is, and signed by the device that added it. Playing one sends nothing through LiveKit: the app tells the others in the room which sound, sealed under the room's group's key, naming who played it and signed by their device, and each of them plays the file themselves. The server passes it on to those in the room without keeping it, and refuses it from someone muted or deafened, by themselves or by an admin, or more often than every two seconds. Apps play a sound only once, and not if it names someone other than whom the server says played it, or is more than five minutes from now by the player's clock.
- **Push to talk from another window** listens only while someone is in a call with it on, or while choosing its key, and only the one key asked for is passed on: on Windows through its low-level keyboard and mouse hooks, on macOS through a listen-only event tap, which needs Input Monitoring, and under Wayland through the global shortcuts portal, where the compositor binds that one key and only says when it goes down and up.

## Calls in direct messages and groups

A call is a conversation's own room on the same media server, keyed from that conversation's MLS group exactly as a voice channel is from its own, so everything above holds for it: whoever is in the conversation can hear it, and nobody else.

- **Who hears of a call.** Who's in it, whose devices it's ringing and who declined go only to the conversation's members, never to everyone on the server, as a voice channel's do. The server itself sees all of it, and when, as it sees who's in a voice channel.
- **Waking a phone for a call** goes through the push relay and Apple, sealed as any push is, with the conversation's ID and who started the call. They can tell a call's push from a message's, so they learn that a phone is being rung, and when, though not by whom or in which conversation.
- **Ringing is the server's word.** A server can say someone is calling who isn't, or not ring someone. Answering a call nobody made comes into an empty room, and can't let anyone hear anything: the media key still comes from the conversation's group.
- **Admins have no say in a call**, which is between the people in it: muting someone for everyone, disconnecting them and stopping their share are for voice channels. The server's rules on sharing a screen hold in calls too, and a ban takes someone out of their calls.

## Watching together

A voice channel or a call can watch one YouTube video at a time, at the same moment on every device that chose to (`docs/WATCH_TOGETHER.md`). The video never passes through Zuna: each device plays it from YouTube. What goes through Zuna is which video, playing or not, where, at what speed and who changed it, with the title and a small picture when the video changes.

- **Sealed and signed as a played sound is.** A signal is sealed under the room's group's key for its current epoch, kind `watch`, and signed by the device that sent it. Apps take it only if it opens, was signed by the device the server says sent it, which the log of keys names, is within two minutes of now by the server's clock and hasn't been seen before. What it says goes through `parseWatch` in `validate.ts`: a video's ID must be YouTube's eleven characters, as it goes into the player's address, and a picture must be an inline JPEG, PNG or WebP of at most 48 KB.
- **What the server sees.** That a device in the room sent a signal, when and how big, and, for an answer to someone coming in, to which device. It passes each on to the room's other devices, or the one it names, without keeping it, and refuses a bot, someone not in the room, more than 64 KB, and more than eight a second from a person after forty. Being muted or deafened doesn't matter. Each voice channel has a switch for it, which only its admins change.
- **What YouTube sees.** Nothing, until a device's person presses Watch, which they're asked about once, with what Google learns, and which a switch in Privacy remembers. Then: the device's IP address, which video, when, how it's played, and the Referer, which in the web app is the web app's origin and in the native apps the app's ID. The player is YouTube's privacy-enhanced one, `youtube-nocookie.com`, in which nobody is signed in. Whoever puts a video on has their device fetch its page for the title and picture, as a link's preview is fetched, so YouTube sees that device's address, or in the web app `zuna-web`'s. The web app, the iPhone and iPad app and the desktop app on macOS, Windows and Linux have it so far. With a SOCKS5 proxy set, the desktop app on macOS plays through it, so YouTube sees the proxy's address, and on Windows and Linux it doesn't play at all (below).
- **The player can reach nothing of Zuna's.** It's a frame of YouTube's own origin, sandboxed to run its scripts and open YouTube in a new tab, and nothing else. Zuna's page runs no script of YouTube's: it drives the player with the `postMessage` messages YouTube's own script would send, and checks what comes back, which is only ever times, states and errors, as anything from outside is checked. The web app's content security policy allows that one frame and nothing else of YouTube's.
- **In the desktop app on macOS** the player is the same page in a WKWebView laid over the window, loaded under `https://chat.zuna.desktop`, with the same limits as on iPhone and iPad below; a link pressed in it opens in the default browser. So that the room doesn't hear the video back through someone's microphone, the app taps the sound of WebKit's own processes, which macOS holds it responsible for, and nothing else, for its echo canceller alone: it isn't sent or kept. That's macOS's permission to record the computer's sound, which it asks for the first time.
- **In the desktop app on Windows** the player is the same page in Microsoft's WebView2, a child of the app's window over the stage, answered from the app's memory under `https://chat.zuna.desktop`, the only address it loads in its main frame. It runs InPrivate, so no cookie or storage outlives it, and its few files are in the app's cache, which the app empties as it starts and quits. Its limits are macOS's: YouTube's player alone in its frame, any link pressed in it in the default browser, no window, no download, every permission it asks for refused, and messages taken from the page alone, each checked. Windows 11 comes with WebView2; without it, the tile says where to get it. Its sound doesn't reach the echo canceller yet, so someone on speakers may send the video back to the room.
- **In the desktop app on Linux** the player is the same page in WebKitGTK, in a window of its own, as nothing can be put inside another program's window under Wayland. That window is `zuna-watch`'s, a program beside the app (`apps/desktop/watch`), which the app starts when its person presses Watch and speaks to in lines of JSON over its pipes, so the app itself never links WebKit. It loads the page under `https://chat.zuna.desktop` in an ephemeral web context, which keeps nothing, with WebKit's web processes in bubblewrap where bubblewrap and user namespaces work; frames YouTube's player alone under the page's content security policy; opens a link or a new window in the default browser; refuses every permission WebKit asks for, the camera, the microphone and the location among them; cancels downloads; and has no developer tools. It hands the app only what the page posts and a few words of its own, and the app checks the page's as on macOS. WebKitGTK doesn't say which frame posted, so YouTube's frame could post too, but only what its player could already say of itself by playing or pausing. Anything else the window's process or WebKit's print goes to the app's log, never into what the app reads. So that the room doesn't hear the video back through someone's microphone, the app takes what WebKit's processes under `zuna-watch` play from PipeWire, which knows them by the sandbox WebKit started them in, and nothing else, for its echo canceller alone: it isn't sent or kept. A screen share's sound leaves it out with the rest of Zuna's.
- **On iPhone and iPad** the player is in a WKWebView that holds `watch.html` from `packages/watch` and nothing else, loaded under `https://chat.zuna.mobile`, which is the Referer YouTube is given, the same for everyone. It keeps no data between sessions, may frame YouTube's player alone under the page's own content security policy, opens any link pressed in it in Safari, opens no window of its own, downloads nothing, and is refused the camera and the microphone. It says only a few kinds of message to the app, which checks each.
- **Who changes it.** Anyone in the room can put a video on, pause it, seek, change its speed or stop it: there's no host. A member could say a change was someone else's in an answer to someone coming in, which only shows a name. Someone outside the room can't send anything there.
- **The clock.** Each device measures how far its clock is from the server's, from the pongs to its pings, and keeps what the quickest round trip said. A server that lies about the time can only put people out of step. It learns nothing by it.

## Presence and phone notifications

Which of your devices you're using, and when you last used each, decides when the others are notified, so the server knows it, whether or not you hide your online status from other members. It also decides that status, as Telegram decides it: you show as online while you're using Zuna on one of your devices, which on a computer is its window in front with input in the last 30 seconds, and on an iPhone the app on screen. As soon as you stop, you show as offline, last seen then. Quitting the app, or closing the web app's tab, is stopping. A connection that drops while you're using it keeps you online for 5 seconds, in case it comes straight back. A device that's only connected, as a phone woken for a notification is, doesn't count. You're online only on the server whose chats you're looking at, as Telegram is only in the account shown. And as on Telegram, whoever sees you send a message, type, or read their messages in a direct message sees you online for 30 seconds after, then as last seen then, or "recently" if you hide it. That's worked out in their app from what it already saw, so the server learns nothing from it, and nobody else sees it.

The server knows which devices get pushes, and through which relay. Until Apple lets the iPhone app filter notifications, it also knows which chats a phone muted and until when, among them direct messages with people the person blocked, which look like any other muted chat. It learns that a chat was read, which stops a push waiting for it. Every push waits about a second and a half, as it isn't told who sent the message, and the sending device reads it at once, which spares its person's phones (above). It keeps which chats each phone was notified about since they were last read, so that it can tell the phone to clear them once they're read on another device: with a silent push, and whenever the phone asks which those chats are, as iOS doesn't always hand a silent push over. A push carries only the message's IDs, or which chat was read and when, sealed for the device.

What a notification says is worked out on the phone, by the app's own core in the notification extension (`previewPush` in `packages/core/src/push.ts`). It fetches the one message with the device's session, opens it with its epoch's key from the app's database, and checks the signature inside and whether that device could have sent it then, as the app does. A conversation moves to a new epoch while the app sleeps, whenever someone's device comes or goes and once a week, and the extension then holds no key for it. It asks the server for the commits in between and applies them, in memory, to a copy of that one conversation's MLS state, takes the key from MLS as the app would, and lets all of it go. It writes nothing, so the app applies the same commits itself when it next runs, with every check it makes of them. The extension follows only where it needs none of those: not past a commit that changes a group's roster, nor one that was undone, and in an epoch it followed to it takes a message only from a device it knew already, whose signing key has a leaf in that epoch's tree. Anything else, such as a message from a device that signed in since the app last ran, shows as "New message" with the chat's name and picture, and nothing of who wrote it, until the app has been opened.

The relay gives each server its own handle for a phone, sealed with the relay's key, so servers can't tell through them that their members' phones are the same, and a push over a phone's limit is answered as if it were sent, so that its limit doesn't tell them either. A handle works for 60 days after it was made, and the app makes new ones each week that it's opened. Until then a server someone left can still push to their phone, a couple of times a second at most, and ring it a few times a minute. The extension can't open such a push, so it shows only that a message arrived, without a sound and without counting on the badge, as the app can't hide it until Apple lets it filter notifications. A VoIP push has to reach CallKit all the same, so it shows as a call from Zuna that ends at once.

## Disappearing messages

How long a chat's messages last is part of its details, signed by whoever set it: in a group only an admin's device counts, and in a direct message either person's. Each message then says how long it lasts, under its sender's signature, and tells the server when it's due. Every device erases its copy, with what search and the chat's details knew of it, once it's due, counting from the earlier of the server's time and the sender's own, so neither can make it last longer. An edit can't change it, and a copy the server sends again stays gone. The server removes its own copy and the message's files within a minute of that.

## Files

Each file gets its own random key. It's split into 1 MiB chunks encrypted with XChaCha20-Poly1305 in the STREAM construction, which detects reordered, missing or truncated chunks. The key travels inside the encrypted message, with the secret the file was made with, which the message shows the server to carry it. Apps keep what they decrypt by the file and the key it opens with, never its ID alone, which everyone in a chat it was sent in and the server know: a message elsewhere naming the same file with another key isn't shown the copy, as if its sender had sent it.

## Metadata in files

The server can't read files, but everyone who receives one can, and so can anyone they pass it to. So before a file is sent, the sender's device takes out what it says about where, when and on what it was made: the place, the camera or phone and its serial number, dates, the program, editing history, comments, and the thumbnails some cameras keep of the picture as it was before it was cropped. This covers photos (JPEG, PNG, WebP, GIF, HEIC and AVIF), videos (MP4, MOV, 3GP, WebM and MKV), and drawings (SVG), along with pictures inside a drawing. A video loses its tracks of timed metadata too, where some cameras record where they were at each moment, and anything a phone adds after a photo's end, such as a motion photo's video. Nothing is compressed again: what a photo or video shows stays as it was, byte for byte, and so do which way up it goes and its colors. A drawing keeps what's drawn, without what drawing programs keep for themselves, such as layer names and the paths of files on the sender's disk.

This is on unless someone turns it off on a device, in Privacy settings, which first says what files will then show and asks to be sure. Other files, such as documents, sound files and RAW photos, are sent as they are, and so is a file that doesn't read the way its kind should. What a picture shows can't be taken out, and nor can the faint pattern a camera's sensor leaves, which can tie photos to the camera that took them.

## Link previews

The sender's device makes a link's preview while they write: it fetches the page, and the title, description and a small picture travel encrypted inside the message. Recipients never contact the site, and the server never sees the link. The site sees the sender's IP address, as it would if they opened the link, and from when the link is typed, even if the message is never sent. Pages are fetched without cookies, only over HTTPS, and only from public addresses: redirects are checked one at a time, and names that lead to this machine or a private network are refused. What counts is where each connection really went, so a site's DNS can't switch where it points between the check and the fetch: the desktop app connects through a small proxy of its own, which reaches only the address it checked, and the iPhone and iPad app drops what it fetched if the system says it came from this device or a private network. When the system is set to use a proxy for a link, that proxy decides where the connection goes, and so does the SOCKS5 proxy a device is set to go through (below), as it resolves names itself: through one, a link is refused by its name and its address as they're written alone. Previews can be turned off on each device.

In the web app, the page can't fetch other sites, so its host, `zuna-web`, fetches pages for it by the same rules, and only on port 443. It checks the address a name leads to as it connects. The web app's host therefore sees which links are previewed, and sites see the host's address instead of the sender's. The chat server still never sees them. A host can turn previews off.

A preview's title and picture are the sender's claim about the page, like the message's text, so a card can say anything. The app only shows a preview for a whole link in the message's own text, always shows which site that link really goes to, and requires its picture to be inline: a preview can't make your device load anything.

## Shared locations

A shared location is where the sender's device said it was, sent inside the encrypted message like its text. The app only asks the system where it is when someone chooses to share it, and shows what it found before sending. Nothing in a message loads a map, since that would tell a map's server where people are looking: the app shows the coordinates, and only opening them, on OpenStreetMap from the desktop and the web app or in Maps on iPhone and iPad, tells that service.

## Forwarding

A forwarded message is a new message from whoever forwarded it. On the same server it names the original author, and its files aren't uploaded again: the copy refers to the same encrypted file, with the secret it was made with, which travels inside the message, so the server can tell that a file was forwarded, though not what's in it. The file stays until the last message using it is deleted. Forwarded to another server, a message only says it's forwarded, and its files are uploaded there again. The "forwarded from" label is the forwarder's claim, as in other messengers.

## Data on your device

Sensitive local data is encrypted with a device key held in your OS keychain (DPAPI, Keychain or Secret Service), each value naming the table and row it's in, so it can't be moved elsewhere. What decides whom to trust is sealed the same way: pins, verifications, how far along each person's chain of keys this device is, what the log of keys says of each account and the head held of it, and when each device came and left each conversation. Chains are checked again from the pinned key each time the app starts. Something outside the app changing any of it gets a warning and the most careful reading. Rows taken out, or the whole database put back as it was, can't be told apart from what the device did itself. The search index stores keyed hashes of words instead of readable text, and the index of each message's photos, files and links, and of which ones mention you or reply to you, names their kinds the same way, though how many a message has is in the clear. If Linux has no keychain available, the app warns you in Settings, because this protection is weaker there, and seals the same key once one is. Started with the login, it waits up to 20 seconds for the keychain first.

Files are decrypted to disk only to be shown, played or saved. The desktop app keeps them in a `cache` folder in its data folder, with the voice and video messages it records and the pictures pasted into it, and empties that folder as it starts and as it quits. A voice or video message it recorded goes from there once it's been sent. iOS keeps its decrypted files in a folder of their own, emptied each time the core starts. The web app keeps them in memory.

The web app has no keychain to use, so its device key is in the browser's own storage, next to the data it protects. Anyone who can copy the browser's profile can read that data, and Settings says so.

On the iPhone and iPad, the share extension uses the same data and device key as the app, from the same Keychain group, and asks for Face ID or the passcode first when App lock is on. What it hands the app while the app is awake is sealed with a key from the device key. Files being shared wait in the App Group until they're sent, as readable as they were in the app they came from.

## The web app's host

- **The web app's host is never a chat server.** It runs as its own program, `zuna-web`, on an address of its own. A chat server, or someone who breaks into one, can't change the code, and its pages can't reach the web app's storage.
- **It loads nothing from anyone else**, but YouTube's player, in a frame of its own, once someone presses Watch on a video their room watches together. Every file comes from its host, under its content security policy: no inline scripts, and images only from memory. The host also sends `frame-ancestors 'none'`, `X-Frame-Options`, `Cross-Origin-Opener-Policy` and `nosniff`, and pages it fetches for previews are marked so they can never run as pages there.
- **A copy can be checked.** A build lists the SHA-256 of every file the web app serves (`zuna-web-files.sha256`, from `npm run build:web`), and `scripts/check-web.mjs` compares a running copy with it. No release carries that list yet, so for now it's whoever built a copy that can check it. This shows what the host serves when you check, not what it serves to everyone at every moment.

[WEB.md](WEB.md) says how to run it.

## A proxy

Sealed sender keeps the server from being told who sent a message, but it still sees the address each device connects from, and so does LiveKit in a call. A device can be set to send everything through a SOCKS5 proxy of its person's choosing instead ([SOCKS5.md](SOCKS5.md)): the desktop app and the iPhone and iPad app in Settings, Privacy, and on their first screen, before any server is joined, so that even signing up goes through it; `zuna-bot` with `--proxy`.

- **One setting for the device,** for every server on it, outside any account. On the desktop its address, port and username are in `settings.json`, and its password is sealed as the device key is (`apps/desktop/src/host/device_key.rs`). On the iPhone they're in the App Group and its password in the keychain group the notification and share extensions share, readable after the first unlock since the phone started and never leaving it, so the extensions go through the same proxy (`Zuna/Shared/ProxyStore.swift`), each reading it before its core starts.
- **Everything or nothing.** Every HTTP client the desktop app makes starts from one function, which sends it through the proxy (`client` in `apps/desktop/src/host/net.rs`), and the core's socket connects through a SOCKS5 client of the app's own (`host/socks.rs`), with TLS and any pin over that, as before. That covers the core's requests, signed-in and sealed, its socket, link previews, icons, emotes, the plugins' marketplace, what plugins fetch, and updates. On the iPhone, the system's own SOCKS5 carries it (`ProxyConfiguration`, failing over to nothing): every `URLSession` the app and its extensions make is made through it and made again when it changes (`ProxiedSession` in `ZunaHost/NetworkProxy.swift`), the core's socket's parameters take it, and so do the push relay's requests. The system takes no proxy to the device itself: to `localhost`, its loopback, link-local and unique local addresses and the addresses it has on its networks it connects straight there whatever the proxy (tried on macOS, docs/SOCKS5.md), so under a proxy the app refuses a server or a link there itself (`goesAround`). While the proxy can't be reached, or refuses the password, nothing connects, and the app says so where it would say it's offline: there's no going around it. Changing the setting ends every connection, and each opens again the new way.
- **The proxy resolves names.** The device never looks a server's name up itself, which would show its resolver, and sometimes part of its own address, to whoever runs the name's DNS. So link previews, and what plugins fetch, are refused by names and addresses as they're written, and where a name leads is the proxy's to decide.
- **What it doesn't hide.** Sealed requests and the session's leave the proxy from the same address, so a server can pair them by it, as it can today. The proxy learns the device's address, which servers it reaches, when and how much, and nothing of what's sent, which stays under TLS and end-to-end encryption. SOCKS5 has no encryption of its own: between the device and the proxy, the server's name and the proxy's password travel as they are, which a proxy on the same machine, such as Tor or `ssh -D`, has no stretch for. Timing is untouched.
- **Calls go through it too, though LiveKit's SDK can't be told to.** So the SDK is only ever told addresses on this device (`apps/desktop/src/voice/proxy.rs`, and on the iPhone `ZunaHost/CallProxy.swift`). Its signalling goes through the app's own WebSocket and HTTP clients, through the proxy: on the iPhone, where the SDK makes its own connection, it's given an endpoint of the app's on loopback, at an address with a secret made for that call, which opens the real one through the proxy. Each message is rewritten by code the core holds for every app (`packages/core/src/voice-relay.ts`): from LiveKit, the STUN and TURN servers go, as does any other address to try, and each of LiveKit's candidates becomes a relay on loopback; from the app, every candidate of the device's goes, from offers, answers, the state it resyncs with and the join request in its address, and every candidate it trickles is dropped, so LiveKit learns where the app is from the first packet that reaches it, which comes from the proxy. A kind of message the rewriter doesn't know is dropped. Each relay, which takes connections from this device alone, carries what libwebrtc sends it through the proxy: TCP over a connection the proxy opens to LiveKit's 7881, UDP in an association of its own for each of libwebrtc's sockets, asked for by a SOCKS5 client of the app's own on the iPhone too (`ZunaHost/Socks.swift`), as the system's has none. The rewriting runs in a JavaScript context of its own beside the core's, on the iPhone as on the desktop. A proxy that grants no UDP association, as Tor and `ssh -D` don't, gets no UDP candidates, and the call goes over TCP, which a lost packet holds up; the stream stats say which.
- **Watching YouTube together,** whose player makes connections of its own: on macOS and the iPhone its web view's data store is given the same proxy (`proxyConfigurations`, `platform/macos/watch_view.rs`, `Zuna/Voice/Watch.swift`), signed in and never failing over. On Windows and Linux nothing takes it there yet, so the app doesn't play a video while a proxy is set. On Windows, the Authenticode check of a downloaded update asks the certificate authorities about revocation through the system, outside the proxy.
- **Where there's none.** Apple's push service, which the system holds, and through which no server sees a device's address. The web app can't have one: what a browser sends follows the browser's or the system's own proxy, and a call in a browser may still go straight to LiveKit, so the native apps are the ones to use for this.

## The desktop app

The desktop app draws its own interface with GPUI, without a web engine, so nothing a message carries can run as code in it. What a message says is checked in the core (`validate.ts`) before anything shows it.

### Updates

On Windows the app updates itself from the repository's releases on GitHub (`apps/desktop/src/platform/updates.rs`, [RELEASES.md](RELEASES.md)). GitHub, and the connection to it, are trusted for nothing but being there:

- **A release is its manifest,** `update.json`: its version, build number, channel, and its installer's name, size and SHA-256. `update.json.sig` is an Ed25519 signature of the manifest's bytes, and `update.json.sig2` an ML-DSA-65 one (FIPS 204), which a quantum computer doesn't forge as it would Ed25519. Builds from before the second check the first alone, as they always did, so every installed build still updates.
- **The app carries the public keys,** four for each channel, an Ed25519 and an ML-DSA-65 pair: the ones in use, and spares whose private halves were never on GitHub. The private keys in use are secrets of two GitHub environments, `UPDATE_SIGNING_KEY` and `UPDATE_SIGNING_KEY_PQ`, which only the release workflow's publishing job reads, for `v*` tags.
- **Its checks, in order:** both signatures, by keys of the same channel, before anything in the manifest is read; that the manifest's channel is the one its key may sign, and one this app follows; that its build number is higher than the app's own; that its tag and file name are what a release's are; then the downloaded file's size and SHA-256, and those again right before the installer runs.
- **An app on stable takes only what a stable key signed.** One on nightly takes either. So whatever cuts nightlies can't reach anyone who didn't choose them, as long as it can't reach the stable key.
- **A build number only goes up,** being how many commits `main` has, so an old release can't be served again as a downgrade, and going from nightly back to stable waits for a stable release that's newer.
- **Nothing can swap the keys or the address** in a build anyone uses: no environment variable, file or setting. Only a build made with the `update-check` feature, for the update's own check, reads them from its environment.
- **Authenticode is a second lock.** Where the running app is signed, an update must be signed by the same publisher, by the whole of its certificate's subject and issuer, with revocation checked. No build is signed yet.

What it doesn't cover: whoever can push a `v*` tag to the repository can release, as the workflow that signs is read from the tagged commit. Both maintainers can, and a stable release waits for no second person. A stolen maintainer account could ship an update to everyone. The spare keys are for moving to after a key leaks, which takes a release signed with the old key that carries the new one.

On Linux and macOS the app doesn't update itself.

### Plugins

A plugin is a package someone installs into the desktop app (`apps/desktop/src/plugins`, [PLUGINS.md](PLUGINS.md)), run as JavaScript in QuickJS. What it can reach is drawn on purpose:

- **A process of its own for each plugin.** The app starts its own executable again as `zuna --plugin-host`, once the window is up and the core has booted, one process for each plugin. That process loads no account, opens no database, reads no file, reaches no network and never holds the device key: its only way out is a pipe to the app, of length-prefixed JSON, and the pipe a message comes on is the only thing that says which plugin sent it. QuickJS is C, and plugins bring it code written to break it, so a break in the engine lands where there are no keys. The runtime has a memory limit (64 MB), a stack limit (1 MB), and an interrupt handler that ends a script running past its deadline (one second) without yielding; over its memory, the process ends; three missed deadlines in a row, or more than 2,000 messages to the app in a second, turn the plugin off. The process isn't confined by the system yet: a job object, seccomp and Landlock, or a sandbox profile, are still to come.
- **A broker checks every request** (`broker.rs`): is the plugin running, does what the person granted cover it, are the arguments the shape and size they should be. Core calls go through the same RPC the interface uses, against a table in the SDK (`packages/plugin-sdk/src/surface.ts`) that names, for every method `rpc.ts` lets an interface call, the permission it needs or "never", typed against the core so a new method doesn't type-check until it's classified. What the table never allows: keys of any kind, `voiceKey` and LiveKit's access among them; passwords, recovery and the account's life; devices, verification, the question a new device raises and the log of keys; bots' setup and a server's administration; a method that fetches a URL through the core. A call's arguments never hold a path (`$file`), and a message a plugin sends carries only text, a reply, mentions and emotes: no buttons, no signal.
- **What plugins are told is cut down.** A message is its ids, its sender's ID as the app worked it out from its signature, its text, its times, and its files' names, types and sizes: never a file's key or path, nor anything named as a secret. Events reach only plugins whose permissions cover their kind, and `voice_key`, `security`, `new_devices`, `button`, `activity` and `preferences` reach none.
- **Drawing is the app's.** A plugin sends trees, which the app draws with its own components, held to 2,000 nodes, 24 levels and 200,000 characters, with only the nodes and props there are. A plugin's dialog, panel and page sit inside a frame the app draws, with the plugin's name and, if it isn't verified, an "Unverified" mark. Nothing a plugin draws shows while the app asks about a new device, verification or a plugin's install. A plugin can open a dialog, a panel or a page, put text in the message box, or use the clipboard or a file dialog only for ten seconds after the person used one of its commands, buttons or views. Its toasts come under its name, five in ten seconds at most. A decoration changes how a message looks on this device alone: where it replaced the text or hid it, the app says which plugin did, in a line the plugin doesn't draw, with one click to the original, and the sender's name, picture, badge and verification stay the app's.
- **Filters say what happens when they fail.** A filter on what's sent that doesn't answer within 1.5 seconds, or throws, is left out, and what it was asked about goes as it was, with a toast naming the plugin. One the plugin registered as required holds it instead, back in the message box.
- **The network is the broker's,** for a plugin with `network` alone: HTTPS to the hosts its manifest names, by name, on the usual port, through the app's own certificate rules, with no cookie and nothing of the account, redirects only to another of its hosts, and names refused if they lead to this machine or a private network, as link previews refuse them, but for a plugin a developer loaded from a folder. At most 1 MB goes out and 8 MB comes back.
- **What's installed is sealed.** `plugins/installed.sealed` holds each plugin's id, version, package hash, origin, what it was granted and whether it's on, with the switch for unverified plugins and the highest index serial seen, sealed with a key made from the device key. Each plugin's storage and settings are in `plugins.db`, each value sealed with a key made from the device key and the plugin's origin and id, so a plugin from a file that borrows a verified plugin's id never reads its data, within 4 MB. A package is hashed again each time it's loaded, and one changed on disk doesn't run. A package asking for more than it was granted doesn't run until the person agrees to it as a new version.
- **Safe mode.** `zuna --no-plugins` starts without plugins, and so does the app by itself after two starts in a row that didn't finish with plugins on. Updates don't pass through plugins: `platform/updates.rs` has no slot, filter or event.

A verified plugin's source is in `zuna-app/plugins`, where its `REVIEW.md` says what it's read against. Its CI builds the package from that source with a lockfile and signs it, and its signature covers each file's SHA-256 under a label of its own (`zuna-plugin-package/v1`). The key is a lasting hybrid key, Ed25519 and ML-DSA-65 from one seed (`zuna_crypto::hybrid`), the private half a secret of that repository's `publish` environment, with a spare whose private half was never on GitHub (`PLUGIN_KEYS` in `plugins/trust.rs`). These keys sign nothing but plugins and the index, and the update keys never sign a plugin. A package with a good signature is verified wherever it came from.

The marketplace is a signed index, `index.json` with `index.json.sig` under the label `zuna-plugin-index/v1`, published with the packages as a release of that repository. The app checks, in order: the index's signature, before anything in it is read; that its serial isn't lower than the highest it has seen; then for a package, its size and SHA-256, its own signature, and that its manifest says what the index said: id, version, permissions, hosts. The index withdraws a plugin, a version of one, or any package by its hash, from every device that has it, the next time it's read. A device reads it only when the person opens Browse, or, with a verified plugin installed, every six hours, at the same host as its updates. A verified plugin updates itself when the new version asks for nothing more; one that adds a permission or a host waits for the person.

What this doesn't cover: whoever controls the connection can keep showing the last index the app saw, hiding a new withdrawal for as long as they can. One maintainer reviews, merges and publishes a plugin, so one stolen maintainer account could ship one. A plugin with the permission to read messages and the network can send them where its manifest says, which review is for; an unverified one, nobody reviews. A plugin can draw a box asking for a password inside its own frame.

### Telegram

A device can link its person's own Telegram account (`docs/TELEGRAM_PLAN.md`, [TELEGRAM.md](TELEGRAM.md)), on Windows, Linux and macOS, and an iPhone or iPad from iOS 26. Its chats are Telegram's cloud chats, not end-to-end encrypted, and each says so. No Zuna server stores, relays or hears anything of it, and nothing passes between its chats and Zuna's: the core refuses a forward either way, and every Telegram method is "never" for plugins (`TELEGRAM` in `packages/plugin-sdk/src/surface.ts`), which reach nothing under the server ID `telegram`.

- **TDLib runs in `zuna-telegram`,** a program beside the app (`apps/desktop/telegram`), which the app starts only on a device with a linked account, so the app links none of TDLib. A device that never links one never runs it and never contacts Telegram.
- **In a box on Windows** (`apps/desktop/src/platform/sandbox.rs`): an AppContainer with no capabilities, one for each data folder, granted that folder alone. Only its three pipes are inherited; it has no console, may start no process, and runs with strict handle checks, no extension points, no fonts but the system's, and no images from a share or of low integrity. Its job object ends it with the app, holds it to one process and 4 GB, and keeps it from the clipboard, the desktop and other processes' windows. Unlinking deletes the container. A build with the `probe` feature tries from inside what the box must refuse, which `platform::sandbox`'s test runs: the app's files, the home folder, the internet by address and by name, Telegram's own addresses and starting a program were each refused.
- **In a box on Linux,** made of what the kernel gives any program, in two halves. The app's, between fork and exec: namespaces of its own for a user, the network and System V IPC, so the only network it sees is its own loopback, where the door is, and none of other programs' shared memory or abstract sockets; Landlock, which lets it open its folder and its own program and nothing else, and from kernel 6.12 keeps its signals and abstract sockets inside; no new privileges, no core dump, 4 GB of memory, nothing the app has open but its three pipes (`close_range`), and its parent's death as a SIGKILL, so that it ends with the app, as Windows' job ends it. The engine's own, on its one thread before TDLib does a thing (`telegram/src/lockdown.rs`): not dumpable, so nobody attaches to it; Landlock for TCP from kernel 6.7, no port but the door's to bind or connect to, which is what holds it in where a distribution keeps namespaces from programs; and seccomp, which refuses starting a program, making a process, ptrace, namespaces, mounts, io_uring, BPF, kernel modules, any socket but TCP over IPv4 and IPv6, and any signal but to itself. Its program is linked whole, C library and all, so it reads no file of the system's. Without Landlock, or without both namespaces and Landlock for TCP, the app offers no Telegram (`sandbox::supported`). The same probe, run so on kernel 7.3: the app's files, the home folder, the internet by address and by name, Telegram's own addresses, another port, UDP, a local socket, a signal and ptrace to the app, a namespace, a process and starting a program were each refused.
- **In a box on macOS,** Seatbelt, the kernel's sandbox that Safari's and Chromium's renderers run in, with a profile of the engine's own (`telegram/src/seatbelt.rs`), which it applies to itself through `sandbox_init_with_parameters` with its door's port bound and before it reads a byte: everything is refused but its own folder, by the name the system gives it, the system's random numbers and the null device, its own loopback at the door's port alone, its own signals and what it is, and a short list of the kernel's facts about the computer, such as how many processors it has. So it reaches no file of the person's or the app's, no service of the system's (the keychain, the clipboard, the window server, the name server and every other one launchd lends), no other process, and makes none. Before that it forbids a core dump and anyone attaching (`PT_DENY_ATTACH`), and has the kernel tell it the moment the app's process ends, which ends it, as Windows' job and Linux's signal do. The app's half (`platform/sandbox.rs`): it starts the engine with `posix_spawn`, every descriptor closed but its three pipes (`POSIX_SPAWN_CLOEXEC_DEFAULT`) and an empty environment, then asks the system from outside (`sandbox_check`) that the engine is boxed, may not read the app's data folder and may not make a process, and sends it nothing, its database's key least of all, until it is; a system without either call has no Telegram (`sandbox::supported`). In the bundle the engine is a program of its own in `Contents/MacOS`, signed under the hardened runtime with no entitlement in any build. The App Sandbox, an entitlement, was the other way: it lets a program reach the network all or nothing, so the door's loopback would have needed the right to connect anywhere. The same probe, run so on macOS 27: the app's files, the home folder, the internet by address and by name, Telegram's own addresses, another port, UDP, a local socket, a signal and ptrace to the app, a process, starting a program, and eight of the system's services were each refused.
- **In a box on the iPhone and iPad,** an extension of iOS 26's, `ZunaTelegram` (`apps/ios/telegram.yml`, `apps/ios/ZunaTelegram`), which the app starts through an extension point of its own (`Zuna/Telegram/TelegramHelper.swift`) that only an extension inside its bundle binds to. iOS runs it as a process of its own in an extension's sandbox, with its own container: it has neither the app group nor the keychain group the app and its other extensions share, so none of Zuna's keys, messages or settings. It's built as Xcode builds enhanced security extensions, and TDLib and OpenSSL with it (`scripts/tdlib.mjs --ios`): pointer authentication in its arm64e slice, typed allocation, stack variables set to zero, libc++'s checks of bounds, and the hardened process's entitlements, a hardened heap and its allocations checked where the phone has memory tagging. It talks to the app over one XPC session. iOS suspends it with the app. A Debug build's helper tries from inside what its box lets it do (`Probe.swift`, the control channel's `telegramProbe`); the simulator runs extensions in no box at all, so only a phone's answers count. On an iPhone 17 Pro Max with iOS 27.0.1, on 2026-11-14: the app's data, its app group, other apps' data, photos, Zuna's keychain items, writing outside its own container and starting a program were each refused; its own folder, its loopback, the internet by address and by name, and the system's random numbers were allowed. Not the extension point's `EnhancedSecurity`, the sandbox Apple gives "data from untrusted sources": asked the same way, it refused writing any file, in the helper's own container too, binding and connecting any socket, its loopback included, socket pairs and kqueues, and descriptors the app sent over XPC never reached the helper, so TDLib could keep no session there and couldn't run at all.
- **A door, not a network.** TDLib's only way out is a SOCKS5 relay inside the engine, carried over the pipe to the app, which opens a connection only to an address in the ranges Telegram publishes (nine IPv4 and five IPv6, `door.rs`), on ports 443, 80 and 5222, and refuses names, so TDLib's ways around a block through other companies' servers are refused too. With a proxy set on the device, every connection goes through it, and with the proxy gone, nothing connects. On the iPhone the relay is the helper's `Door.swift`, carried over XPC to `TelegramDoor` in `ZunaHost/TelegramBridge.swift`, with the same ranges and ports, each part of a connection waiting until the other side has taken the one before. iOS's box doesn't hold TDLib to it: there it's the door because TDLib is set to use it, and a broken TDLib could open a socket of its own past the door and the device's proxy.
- **A broker for every request** (`apps/desktop/src/telegram`, and on the iPhone `ZunaHost/TelegramBridge.swift`, which reads the same list): only the functions in `packages/core/src/telegram/functions.json` pass, some with fields held to values (`setChatMemberStatus` only to leave), at 100 a second with bursts of 500. Never on it: deleting the account, its password, number or email, ending other sessions, payments, contacts from an address book, proxies, TDLib's parameters, raw queries. A frame over 32 MB ends the engine, as does one that misses the watchdog's question every 30 seconds; it's started again, and after three failures in a row it stays off.
- **Its database is encrypted** with a random key, sealed with the device key under its own label (`telegram-key.sealed`), and handed to the engine over the pipe as it starts, so a copy of the disk holds no session.
- **Files go by bytes, never by path.** What's sent is read by the app and written to TDLib a part at a time as it asks for each (`generate` in `session.ts`), under a name made for that send, with metadata removed when Privacy says so; a file TDLib asks for that no send made is refused. What TDLib downloads is handed to the interface only if its real path, links resolved, is inside the engine's folder (`inside_engine_folder`). On the iPhone the app can't read the helper's folder, nor the helper the app's: the helper opens a file of its folder, links resolved and only a plain file, and hands the app the open file over XPC, which the app copies into the cache it empties whenever the core starts (`TelegramBridge.file`).
- **What TDLib says is untrusted.** The adapter (`packages/core/src/telegram/map.ts`) holds every string, number, entity, button and file to its limits and kinds before anything shows it, takes a link's address only over HTTP or HTTPS, a file's name with nothing a path could make of it, and drops updates of kinds it doesn't know.
- **What Telegram learns:** the account's use of Zuna by its `api_id`, the device's IP address or its proxy's, "Desktop", "iPhone" or "iPad" for the device's model and the system's name for its system, and when the person is online, which goes out as Telegram's own apps send it, as its terms ask. Read marks and typing go out the same way.
- **Unlinking** signs out, which ends the session at Telegram, then erases the engine's folder and forgets its key; with no connection the folder is erased all the same and the app says to end the session from another device. A session ended from another device erases it too, unlike a Zuna server, on whose word nothing local is erased: someone who ends a session from their phone, as after losing a laptop, means for what it held to go.
- **The api_id** is compiled into release builds from the repository's secrets, and is in every installer for anyone to read, as in any Telegram client. Only release builds and builds from a checkout with `~/.zuna/telegram.json` have it, and a development build reads the environment and uses Telegram's test servers. An iPhone build without it has no helper at all (`apps/ios/telegram.yml`), and TestFlight's have none yet.
- **Pushes on the iPhone come from Telegram through Apple.** While the app is open the helper is connected and the app notifies, as the desktop does. Closed, Telegram pushes each message straight to the phone, as it does for any third-party app, with a push certificate for Zuna's one bundle uploaded to Telegram: the broker gives Telegram the app's push token as the account signs in and each time the helper starts (`registerDevice`, which isn't on the core's list), and signing out takes it back. Telegram doesn't encrypt an ordinary push for a third-party app, so Apple's push service carries the sender's name and the text, as the linking screen says. No Zuna server, the relay included, takes part. The notification extension tells Telegram's from a server's by its shape, as a server's is sealed under `zuna` with a key Telegram doesn't have, so neither can pass for the other, and words it under "Telegram" (`Zuna/Shared/TelegramPush.swift`); where iOS doesn't run the extension, it words it from the sentences the app carries (`en.lproj/Localizable.strings`). Telegram decides what's pushed, as for its own app: a muted chat isn't, and a silent message makes no sound. Whoever holds that certificate can show a notification under Zuna's name on linked phones, and can't read anything.

What this doesn't cover: Telegram reads everything in those chats. A break in TDLib lands in a process that holds the Telegram session it was already running, and can use it as the account. On the iPhone it can reach the internet too, past the door and the proxy. Telegram may limit an account that uses an unofficial app.
