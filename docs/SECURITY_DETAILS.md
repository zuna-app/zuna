# Security details

How each of Zuna's protections works, for anyone checking them. [SECURITY.md](../SECURITY.md) says what they mean for the people using Zuna, what the server can and can't see, and the limits.

## Group encryption: MLS

Every conversation, including DMs, is an [MLS](https://www.rfc-editor.org/rfc/rfc9420.html) group, using the ciphersuite `MLS_128_DHKEMX25519_CHACHA20POLY1305_SHA256_Ed25519`. The implementation is [OpenMLS](https://github.com/openmls/openmls), compiled to WebAssembly.

Each device is its own member of each group. Keys change at every membership change and at least weekly on active conversations. The server's only role in MLS is enforcing one order of commits per group.

## Message content

Each MLS epoch exports a content key (RFC 9420 section 8.5). Messages are encrypted under it with XChaCha20-Poly1305, padded to 256-byte blocks, and signed with the sender's device key (Ed25519). The signature matters because all members share the content key: without it, any member could impersonate another. What's signed says who wrote it as well as what it says, so a server can't put one person's words under another's name, even with a member's help. Reactions, read positions, pins, deletions and typing signals are signed the same way, and say which message or person they're about. Every signature also names the account and device it's from, so a device key that someone else's certificate names too can't pass one person's reaction off as another's.

Who signed, and the signature, are inside the encryption: an envelope is `nonce || XChaCha20-Poly1305(content key, aad, pad(version || user || device || signature || body))`, where the authenticated data names what it is, the group, the message or person it's about, and the epoch. A signature outside, over the ciphertext, would let the server try each member's device key on it to find whose it is. What's signed is `zuna/envelope-sig/v3|user|device|`, the SHA-256 of the authenticated data, a commitment to the content key (`HKDF(content key, "zuna/envelope-commit/v1")`) and the SHA-256 of the body. The commitment keeps what signing the ciphertext gave: a good signature proves its signer used this very key, which a key from a history grant proves itself by, so a member who opens someone's signed body can't seal it again under a key of their own choosing.

An app opens an envelope, reads whose device it says signed it, and checks the signature with that device's key, so it learns who wrote a message from the message alone, never from the server. One that names a device it doesn't know yet is held, out of sight, until it does. One that doesn't open under a key that has proved itself, or that nobody it names signed, is nobody's: it's kept without being shown, counted or notified about, and never as from whoever it names, so no member can frame another.

## Sealed sender

What a member adds to a conversation tells the server nothing of who sent it: messages, edits, reactions and taking them back, pins and unpins, an author's own deletions, and typing. Nothing the server keeps about any of these says who.

- **No session.** A sealed request carries no session token, cookie or device key. The desktop app, the iPhone app and `zuna-bot` send them on connections of their own, with TLS sessions of their own; a browser decides for itself which connection a request takes, so the web app only leaves its credentials out.
- **The send key.** Each epoch has one, `MLS-Exporter("zuna/send/v1", epoch, 32)`, an Ed25519 seed every member of the epoch can make, and nobody else. Whoever makes an epoch gives the server its public half with the commit, and a sealed request is signed with it over its method, path, time, epoch, token and body, so the server checks it against the one key it holds for the group and can't tell one member's signature from another's. Only the current epoch's key is taken, so someone removed can't write. A device that goes without a commit, as its person leaves, is banned or deletes their account, or as it's signed out, is still in the tree and would make the key until a commit took it out, so the server forgets the group's key as it goes, and takes nothing sealed for the group until a member's commit gives it the next epoch's, which apps send before anything else. The secret is never stored or handed on, and holding old content keys gives no way to make it. Every member checks the server's key against its own when it applies a commit or reads the group, and one that differs, from whoever made the epoch or the server, is put right by a member's commit, as every commit carries one. Undoing commits restores the key with the group info it went with.
- **Tokens.** A limit on a person needs a name, and a limit on a whole group would let one member use it up for everyone, so each sealed request that changes something spends a token: RFC 9497's verifiable oblivious PRF, suite ristretto255-SHA512. A device asks for them while signed in, a hundred small and ten large at a time, a random while after it runs low, never because something is about to go, and the server counts them against that person: a thousand small and a hundred large in six hours across their devices, ten times that for a bot. A small token pays for up to 32 KiB, a large one for anything up to the 256 KiB limit. The server evaluates them blind, under a key of its own for each size and six-hour period, and proves it used the key a request with no session is shown; a token redeems in its own period and the next. Redeeming one shows the server a token it issued and hasn't seen before, and nothing of whose it was. It's spent in the same transaction as the write, so one refused costs nothing. What changes nothing, a message sent again, a reaction added again or a deletion of what's deleted, spends none, and is sent on to nobody, so that it can't be used to have the server send a message to a whole group over and over. Each signed message also carries a short hash of the token keys its sender was shown, and an app whose own differ for the same period warns, as a key made for one person would let the server follow their tokens. Typing spends none: it's kept nowhere, and a limit by group and address holds it.
- **Item keys.** Changing or deleting something takes a key only its author's devices can make: `HKDF(subkey(account key, "author"), "zuna/item-key/v1|kind|group|item")`, an Ed25519 seed. A message or reaction goes up with its public half, which the server keeps beside it, and checks an edit, deletion or reaction taken back against. Item keys can't be told apart or tied to anyone without the account key, so they name nobody. After the account's keys are replaced, a device tries each key it holds, the older ones included. A reaction taken back keeps its ID on the server, without what it carried, as a deleted message does: every member was sent what its author signed, and could otherwise send it again under the same ID with an item key of their own. This only stands in for the server's own check: what apps trust is still the signature inside.
- **Files.** A file a message will carry is made with a secret, whose SHA-256 the server keeps, and the secret travels inside the message with the file's key. A sealed message shows each of its files' secrets, which the server checks, and from then on the file belongs to nobody. Forwarding shows the same secret. Uploading is named, and what each person may upload is counted over thirty days in whole MiB, so no total gives one file's size away. That count is kept by the day, so a copy of the server's data says who uploaded on which day, and on a day only one person did, whose the files made that day were.
- **What a sender's phones aren't told.** The server can't leave the sender's phones out of a push, so every notification waits about a second and a half, and the device that sent the message reads it at once, at its own message, which cancels the push for that person's phones as anyone's read would.
- **Slow mode and reactions.** The server can't hold a person it can't see to a pace, so each app holds its own person to a channel's slow mode, and hides a message from anyone else that came sooner after its author's last than the channel allows, less two seconds for the network, by the server's times. The most reactions one person puts on a message, 32, are held the same way. Tokens bound how much a modified app can send past either.
- **What stays named.** A group admin deleting someone else's message, which needs their role; commits, and undoing them; a group's details; read positions; files being uploaded and fetched; voice and calls; reports. Each is about someone being somewhere, or something the server has to check.

A server that sets out to can often still work a sender out, from addresses, timing and who it didn't have to wake, as [SECURITY.md](../SECURITY.md#limits) lists. The promise is about what the server is told and keeps.

Using exported keys rather than MLS's per-message ratchet is a deliberate trade-off, and it's what makes history on new devices possible:

- **Gained:** a device you add later can read your past messages, and new group members can receive history if an admin allows it.
- **Given up:** forward secrecy within an epoch and, for stored history, against theft of your account key. See "Limits" in [SECURITY.md](../SECURITY.md#limits).

## Keys on new devices

Your **account key** is random. It encrypts your identity keys and a vault of content keys, all stored on the server as ciphertext, each kind under a key derived from it for that alone. It's unlocked by either:

- your **password**, stretched on your device with Argon2id (64 MiB, 3 iterations), or
- your **recovery key**, 200 random bits shown once at sign-up.

Your password never leaves your device. A key derived from it authenticates you, and a separate one opens a key pair that the account key is sealed to, so any of your devices can seal a new account key to your password without knowing it. The first is bound to the server's address and your username, so one a malicious server collects is no use anywhere else, even if you use the same password on several servers. Clients only derive keys within fixed limits, so a malicious server can't downgrade them or make the app run out of memory.

Sealing to that key pair needs no secret, so a server could seal a key of its own to it. What you unlock also names the key your account began with, and signing in only goes ahead with keys that really are that account's. A device that already knows your account also won't give it up for one that began with another key.

## Identity and devices

Each account has one long-term Ed25519 **identity key**. Each device's MLS credential is a certificate signed by it, naming the key that device signs with. Certificates are public, so holding one proves nothing: clients check every member of every group, whenever a group's tree may have changed and before encrypting anything, against the identity key they know for that person, and that the member really signs with the key its certificate names. So without that identity key, the server can't add a device to anyone's account. Whoever tries is removed, and everyone is warned. A leaf nobody can check yet counts for nothing, and nothing is encrypted to a group while one is on its roster. A server can make accounts of its own, as it can sign anyone up, but it can't get one into a conversation. A group's roster (below) says who its admins have let in, and anyone else in its tree is removed before anything more is encrypted. A direct message's two people are settled when a device first sees it, and anyone else in its tree is removed. What you write to someone can't be sent to another conversation either: if the server names one this device knows as something else, nothing is sent.

A device signs in to the server with a session token. Removing a device, a group admin deleting someone else's message, deleting a conversation, leaving one, changing who's a group's admin, managing invites, writing to the vault, replacing the account's keys or anything that carries them to its devices, and anything an admin does also take a signature by the device's own key, so a token found on its own, such as in a proxy's log, can't do them.

Clients pin the first identity key they see for each person, and share those pins, and what you've verified, with your other devices through your encrypted vault. One manifest there lists all of them with your preferences and how far along each person's chain of keys your devices have got, under a number that only goes up. It's one vault item, or for an account that has seen thousands of people several, each naming the manifest's number, how many parts it has and a hash of the whole, and a device takes it only once every part of one write is in, so leaving out a part leaves out the whole manifest. It's the only place any of that is kept, so the server can't leave out one person's pin or verification, and a device that has seen a manifest refuses an older one and says so. An account starts with one, and each replacement of your keys seals its number in, so a new device warns if it's shown an older manifest than that, or none. If two of your devices hold different keys for someone, they warn too. An account moves on from that key only by a signed chain that starts from it. Anything else, including two chains for the same person, produces a loud warning, including on a new device of yours.

## Replacing your account's keys

When a device is removed or signs out, your password or recovery key changes, or someone signs in with your recovery key, your app replaces your account key, identity key and HPKE key, in the background. It seals the new account key to each remaining device and to your password and recovery key, and publishes one signed link from the old identity key to the new one, listing the devices that stay. Contacts follow that chain, and from then on a certificate signed by the old identity key means nothing unless its device is on the list. The vault is sealed again under the new key. The design and what it can't do are in [ACCOUNT_KEY_ROTATION.md](ACCOUNT_KEY_ROTATION.md), and **no independent cryptographer has reviewed it yet.**

## The emoji check

Pinning alone doesn't protect a first conversation: a malicious server could hand out a fake key from the start. The emoji check closes that gap. Two people compare 16 emoji (96 bits, from Argon2id over both identity keys, at the same cost as a password). A server that swaps both people's keys only needs the two sides to agree, so a match is cheaper to find than for one fixed key: the memory Argon2id needs for every attempt, and the 96 bits, put that out of reach. If they match, each app holds the other person's real key, and since every device in a chat has to be signed by that key, nobody else's device can be in the chat as them. Saying they match only ever trusts the key those emoji were made from, so a server can't use that moment to swap in another. After someone's keys are replaced, the emoji change, and a verification only carries over if a device the other person has known for at least a week made the change. Otherwise that person goes back to unverified, and a line in your chat says so.

## Who's in a conversation

The server keeps a list of who's in each conversation, for what it does itself. A group also has a **roster**: who its admins are, and who they've let in, in a private extension of its MLS group context (`ROSTER_EXTENSION` in `crypto/src/mls.rs`, `packages/core/src/roster.ts`). MLS makes every member hold the same one, and only a commit changes it. Each version is signed by the device that made it and names the hash of the one before. Clients check every change before keeping it: an admin may change anything, anyone may take themselves off it, and when none of the admins is left in the group, the one person the server made its admin may take over and change nothing else. Whoever rejoins a group takes its roster only if it's the version held, the next one, or a later one an admin of the held version signed. Group admins are the roster's, for deletions, the group's details, history grants and who may add or remove people. The server's list of admins follows the roster, taken only from an admin's commit. What MLS proves is who actually holds the keys. Clients go by that, and by the roster:

- Someone the roster doesn't name, or a device that isn't what it claims, is removed before anything more is encrypted, and everyone gets a warning in the conversation.
- That someone left is only announced once their keys are really gone. Who removed them is named only if MLS shows it: otherwise, it would be the server's word.
- The member list shows a difference if there is one: someone who holds the keys but isn't listed, or who's listed with no device in the group.
- Only an admin's device can set a group's name and picture, which it signs, and an older copy can't be served again.
- A member can't remove someone from a group's keys: everyone is told, and the person removed rejoins straight away.
- A message under an epoch your device was in the group for only counts as sent by a device that was in the group's tree by then, and not after it left. One that isn't is marked unverified, so a member can't pass someone outside the group a key to write in it.

## What the server can't make your app do

The server can say you're out of a conversation or signed out, but your messages stay on your device until you clear them, sign in again, or 30 days pass. It can say a message was deleted, too, but your app only erases its copy if the deletion was signed by the device of whoever wrote it or, in a group, of an admin. Otherwise the message is hidden as deleted and kept for 30 days. That includes a device you removed from your account in Settings, so a lost device isn't wiped if it comes back online: removing it cuts off its access, not what it already holds. Nor can it pin a message on its own: a pin only shows if a member's device signed it, and only a later pin or unpin, also signed, replaces one your app has seen.

## Deleting an account

Deleting an account takes its password, checked as a sign-in is and counted with the account's sign-in attempts, and a request signed by the device. The server takes the account out of every group, then erases its sign-in and recovery data and their salts, its sealed vault core and vault items, the slots and bundles that carry its account key, history grants, key packages, welcomes, sessions and push registrations, its profile and avatar, and revokes the invites it made. It frees the username, and the account's role becomes member. Its ID, identity key, chain of identity links, HPKE key and devices' certificates stay, with every device revoked: a device that comes later still checks what the account sent against them. Messages, reactions and files it sent stay on the server, which doesn't know which they are, and a direct message with it stays with it, as the server says who each one is between.

Other devices of the account are signed out, with `account_deleted` as the reason, and keep their data as after any sign-out. The device that asked erases its copy once the server agrees. Everyone else's apps take the account's devices out of the trees of their conversations, as after a ban, and show it as "Deleted account", with no picture, in place of what they knew of it.

The server could say an account was deleted when it wasn't. As with a ban, that only hides someone: their name and picture aren't shown, and they're taken out of conversations.

## Reporting someone

A report says whom and why: a user ID and one of a few reasons. It carries nothing of any message, which the server can't read, and the server stores it without who sent it. While it arrives, the server knows whose session sent it, and holds in memory, for a day, that this person reported that one, to refuse the same report again, and how many reports each person sent this hour. Neither is written anywhere. Whom an account reported is in its encrypted preferences, so that its apps don't offer to report them again. Admins see the reports, apart from those about themselves, which another admin or the owner has to look at. A ban, or the account being deleted, clears what it was reported for.

## Bots

A bot is an account, with an identity key, an account key and one device, as a person's has. A program runs it: `zuna-bot` (`apps/bot`), which holds the client core and does MLS for itself, on a machine its owner chose. So a bot is a member of each chat it's in and reads everything said there from the epoch it joined in, on that machine, and the server still reads none of it. [BOTS.md](BOTS.md) is the guide to making and running one, and [BOTS_PLAN.md](BOTS_PLAN.md) the design.

**Setting one up.** The owner's app asks the server for a bot, which reserves its username and makes an invite that works once, for an hour, and only for that bot. The app makes an Ed25519 key pair and builds the setup link: the invite, the community key, and in the link's fragment, which the server never sees, the pair's secret half with the bot's ID, username and name, and its owner's ID and identity key. It keeps the public half, sealed with the rest of what the device stores. `zuna-bot init` signs up with that link: the bot's keys are made there, with 32 random bytes for a password nobody sees, so the server guessing passwords doesn't apply to a bot. It signs `zuna/bot-setup/v1`, its ID and its new identity key with the link's secret, and the server keeps the signature with the account and hands it out with the bot. The owner's device checks it against the public half it kept, and marks the bot verified, as comparing emoji would. A server that signed a bot up itself, with a key of its own, has no such signature to show, and the bot stays unverified. The bot's device pins its owner's identity key from the link, so nobody the server names later is taken for its owner.

**What a bot gets.** Nothing from before it was added: where a group shares its history, `addMembers` hands a person the older epochs' keys and a bot none, and the server refuses a history grant made out to a bot. Its profile, with its commands, is sealed with the community key and signed, as anyone's is. Only the bot can seal it, so its owner's app asks it to, in a message in their direct chat that only the owner's identity key is obeyed for.

**Who may add it, and where it goes.** The server refuses a commit that adds a bot unless its owner allowed whoever sends it: the owner, the server's admins for a listed bot set to that, or anyone. It hands out a bot's key packages only for a chat the bot may be in: to the person its direct chat is with, to someone who may add it to that group, or to a member of a group it's already in. The bot checks for itself when it finds it's in a group, by who added it, and leaves a group it shouldn't be in, so a server that lets someone through gains a member that goes. A bot can't start a group or a direct message, make invites or other bots, take a role on the server, or get a token for voice. A listed bot joins the channels the server says it was given, which is the server's word alone. A private bot's core joins none, whatever the server says.

**Who sees it.** The server leaves a private bot out of everything it tells anyone but the bot's owner and the people in a group with it: the list of users, profiles, key packages and the socket's frames about it. That hides it from people, other admins included, never from the server, which knows every bot, whose it is and which chats it's in. Its username is still taken, which someone asking for the same one is told, as of any name. A bot shows no presence: the server sends none for it, and the core shows none whatever arrives. In a chat, a bot is on the roster as anyone is, so nobody is in a chat with a bot without their app showing it, with its badge.

**Messages nobody is shown.** Two kinds of message carry a `signal` in place of something to read: an owner's changes to their bot, and the press of a button under a bot's message. They're sealed and ordered as any message is, so every member's device receives a press and can open it. The core keeps them out of every chat, shows no notification and stores nothing but that it saw them, and hands a press to the bot's own program. The sender marks them `silent`, which the server reads, to send no push for them, so the server knows which messages these are, though not what they say. Buttons are only shown under a bot's messages, and a link in one is opened as a message's link is.

**Where it runs.** `zuna-bot` keeps the bot's device key in a file only its user can read, as the Linux app does without a secret store, so whoever can read its data folder is the bot. Its API listens on `127.0.0.1` and takes a token from that folder. Its numbers for people, chats and messages are its own, kept in that folder, and mean nothing elsewhere. It fetches no file from an address and makes no link previews, either of which would tell a site where the bot runs.

## Profiles and the community key

Display names and avatars are encrypted under a **community key**, carried in the fragment of invite links (`#k=...`), with a key derived from it for profiles alone, as channels and sounds have theirs. Browsers don't send fragments to servers. Profiles are also signed by their owners.

If an admin turns on open sign-ups, there's no invite link to carry that key, so the app gives it to the server, and the settings screen says so. This exposes profiles, not messages.

## Servers without a domain

Given an IP address in place of a domain, the server makes its own certificate: a P-256 key made once and kept in its data folder as `certificate.key`, and a certificate from that key for each connection, as Chromium remembers its verdict on each certificate for a while. Its links carry the SHA-256 of the key's SubjectPublicKeyInfo, in base64url, in their fragment (`#pin=`), which browsers don't send to servers. The app keeps it with the account, sealed as the rest of it is, and before anything reaches the server, has its host trust that key for that address, and no other certificate for it: the desktop app's host through rustls (`apps/desktop/src/host/tls.rs`), and iOS through URLSession's and Network.framework's, and LiveKit's socket for voice, whose delegate, a private class of LiveKit's, the app gives the same check before a room first connects. The desktop app's LiveKit connection takes only the system's roots, so its voice can't reach LiveKit through such a server yet, and fails rather than trusting anything else. The key decides, not the certificate's dates or names.

- **Only an address over HTTPS can have a pin,** never a name. The core and both hosts check, so no link can have the app trust another key for a name, such as where updates come from.
- **A link can't change the pin of a server the device is on.** Anybody can send a link, and its key would be trusted as soon as it was pasted, before anyone decided to join. A new key needs signing out of the server and in again with its new address.
- **The first link decides.** Like the community key, the pin is only as good as the way the link came. A wrong one, with someone between the device and the server, lets them pose as the server, which E2EE already assumes a server may do.
- **A browser can't check a certificate by its key,** so the web app refuses such a server rather than trust whatever certificate the browser would.

## Channels

Everyone on a server can see and join its channels, so a channel is only as private as the server's membership. What they're called and everything said in them is end-to-end encrypted in the same way as a group's, and the server can't read any of it. The server does see each channel's rules: how many fit, how many may share a screen, whether the soundboard plays there, and its slow mode, which each app holds its own person to, but not admins, and hides a message from anyone else that came too soon (above).

To be in a channel, someone has to show they hold the community key, which comes with invite links and which the server doesn't have. Members check that for each person on the roster, and remove anyone who can't. A server can't get an account of its own making into a channel. Three things to know about that:

- **Open sign-ups** give the server the community key, so there it could.
- **Someone banned** still holds the key. The server takes them off the roster, and members remove them, but a server that wants them back could put them back. They'd get what's said from then on, not what was said while they were gone.
- **Old invite links** carry the key too. Whoever holds one can read channel names if they get hold of the server's data, and can sign up if the invite still works. Nothing else depends on that key.

A newcomer gets a channel's history from a member's device, which signs what it hands over. Any member can do that, since all of them may read all of it, so a member with bad intentions could hand someone a wrong key for an old epoch, and those old messages then wouldn't open. Nothing new is at risk: only MLS's own keys are used for what's sent from then on.

## Voice channels

Media is encrypted in the app with a key from the channel's MLS group, frame by frame, before LiveKit sees it. LiveKit and the Zuna server can't hear or see it. The key exists only for the group's current epoch and is never stored or handed on, unlike the keys to messages: a stolen vault, or someone who joins later, can't open a recording of a call. A device in a room whose epoch has lasted six hours makes a new one, since the nonces frames are encrypted under start repeating after about thirteen hours of video.

- **What they do see.** The Zuna server sees who's in which voice channel, whether they say they're muted, deafened or sharing, and when. LiveKit sees who's in a room, by user and device ID with no names, and from when to when, who's sending what, how big it is, and how loud each person's audio is, since that's what lets it say who's speaking. Frames are encrypted, not hidden: their size and timing can say something about what's being said.
- **Who can hear.** Whoever is in the group. Someone removed goes on being able to open what's sent under the old key for about 1.5 seconds, while everyone moves to the new one. Someone in the room without the key can't open anything: the server can put someone in a room, but not in the group.
- **Who said it.** Everyone in the group can work out everyone's sender key, so a member could send media as another member. LiveKit can't. There are no per-frame signatures.
- **The microphone** is processed entirely on the device. Nothing about it leaves but what's sent.
- **Who can share a screen** is up to each server's admins, and LiveKit enforces it. Coming into a voice channel doesn't allow a screen at all, and the server only allows one after checking its rules, which it can also take back. See [SCREEN_SHARE.md](SCREEN_SHARE.md#what-a-server-says-and-what-a-device-chooses).
- **The iPhone's broadcast extension**, which records the screen before iOS 27, never has a key. It hands frames to the app over a socket in the App Group, which only Zuna's own app and extensions can open, and the app encrypts them. A broadcast started from Control Center goes out only once the server has made room for it, as one from the app's button does.
- **The native screen share** runs in the desktop app's own process and goes out from its own connection, under the device's own key, so its keys never leave the app. libwebrtc's logs stay off in the app unless `ZUNA_WEBRTC_LOG` is set, since the native frame cryptor has been reported to log keys. `apps/desktop/test/key-log-check.mjs` shares a screen with every log on and looks for that.
- **A screen shared in AV1**, an experiment that only the native app sends and opens, is encrypted whole by the same frame cryptor, which leaves no part of an AV1 frame out, and then goes out inside OBUs of its own, so that libwebrtc can packetize it: a metadata OBU holding the ciphertext, after, on a keyframe, a sequence header and a frame header with nothing of the picture in them, which say only that it's a keyframe, as RTP's own header does. The app takes the ciphertext back out before the cryptor opens it (`apps/desktop/patches/webrtc-sys.patch`). H.264 leaves its NAL headers out of the encryption, which say what kind each part of a frame is, so AV1 shows less. `apps/desktop/test/codec-check.mjs` checks that a watcher with another key opens nothing of either codec, and one with no encryption, as the media server is, nothing of AV1; of H.264 a decoder makes a few frames of what it can't open, from those headers.
- **The soundboard** is a server's sounds, which its admins add. Each one's name and the key to its file are sealed with the community key, as a channel's name is, and signed by the device that added it. Playing one sends nothing through LiveKit: the app tells the others in the room which sound, sealed under the room's group's key, naming who played it and signed by their device, and each of them plays the file themselves. The server passes it on to those in the room without keeping it, and refuses it from someone muted or deafened, by themselves or by an admin, or more often than every two seconds. Apps play a sound only once, and not if it names someone other than whom the server says played it, or is more than five minutes from now by the player's clock.
- **Push to talk from another window** listens only while someone is in a call with it on, or while choosing its key, and only the one key asked for is passed on: on Windows through its low-level keyboard and mouse hooks, on macOS through a listen-only event tap, which needs Input Monitoring, and under Wayland through the global shortcuts portal, where the compositor binds that one key and only says when it goes down and up.

## Calls in direct messages and groups

A call is a conversation's own room on the same media server, keyed from that conversation's MLS group exactly as a voice channel is from its own, so everything above holds for it: whoever is in the conversation can hear it, and nobody else.

- **Who hears of a call.** Who's in it, whose devices it's ringing and who declined go only to the conversation's members, never to everyone on the server, as a voice channel's do. The server itself sees all of it, and when, as it sees who's in a voice channel.
- **Waking a phone for a call** goes through the push relay and Apple, sealed as any push is, with the conversation's ID and who started the call. They can tell a call's push from a message's, so they learn that a phone is being rung, and when, though not by whom or in which conversation.
- **Ringing is the server's word.** A server can say someone is calling who isn't, or not ring someone. Answering a call nobody made comes into an empty room, and can't let anyone hear anything: the media key still comes from the conversation's group.
- **Admins have no say in a call**, which is between the people in it: muting someone for everyone, disconnecting them and stopping their share are for voice channels. The server's rules on sharing a screen hold in calls too, and a ban takes someone out of their calls.

## Presence and phone notifications

Which of your devices you're using, and when you last used each, decides when the others are notified, so the server knows it, whether or not you hide your online status from other members. It also decides that status, as Telegram decides it: you show as online while you're using Zuna on one of your devices, which on a computer is its window in front with input in the last 30 seconds, and on an iPhone the app on screen. As soon as you stop, you show as offline, last seen then. Quitting the app, or closing the web app's tab, is stopping. A connection that drops while you're using it keeps you online for 5 seconds, in case it comes straight back. A device that's only connected, as a phone woken for a notification is, doesn't count. You're online only on the server whose chats you're looking at, as Telegram is only in the account shown. And as on Telegram, whoever sees you send a message, type, or read their messages in a direct message sees you online for 30 seconds after, then as last seen then, or "recently" if you hide it. That's worked out in their app from what it already saw, so the server learns nothing from it, and nobody else sees it.

The server knows which devices get pushes, and through which relay. Until Apple lets the iPhone app filter notifications, it also knows which chats a phone muted and until when, among them direct messages with people the person blocked, which look like any other muted chat. It learns that a chat was read, which stops a push waiting for it. Every push waits about a second and a half, as it isn't told who sent the message, and the sending device reads it at once, which spares its person's phones (above). It keeps which chats each phone was notified about since they were last read, so that it can tell the phone to clear them once they're read on another device: with a silent push, and whenever the phone asks which those chats are, as iOS doesn't always hand a silent push over. A push carries only the message's IDs, or which chat was read and when, sealed for the device.

The relay gives each server its own handle for a phone, sealed with the relay's key, so servers can't tell through them that their members' phones are the same, and a push over a phone's limit is answered as if it were sent, so that its limit doesn't tell them either. A handle works for 60 days after it was made, and the app makes new ones each week that it's opened. Until then a server someone left can still push to their phone, a couple of times a second at most, and ring it a few times a minute. The extension can't open such a push, so it shows only that a message arrived, without a sound and without counting on the badge, as the app can't hide it until Apple lets it filter notifications. A VoIP push has to reach CallKit all the same, so it shows as a call from Zuna that ends at once.

## Disappearing messages

How long a chat's messages last is part of its details, signed by whoever set it: in a group only an admin's device counts, and in a direct message either person's. Each message then says how long it lasts, under its sender's signature, and tells the server when it's due. Every device erases its copy, with what search and the chat's details knew of it, once it's due, counting from the earlier of the server's time and the sender's own, so neither can make it last longer. An edit can't change it, and a copy the server sends again stays gone. The server removes its own copy and the message's files within a minute of that.

## Files

Each file gets its own random key. It's split into 1 MiB chunks encrypted with XChaCha20-Poly1305 in the STREAM construction, which detects reordered, missing or truncated chunks. The key travels inside the encrypted message, with the secret the file was made with, which the message shows the server to carry it.

## Metadata in files

The server can't read files, but everyone who receives one can, and so can anyone they pass it to. So before a file is sent, the sender's device takes out what it says about where, when and on what it was made: the place, the camera or phone and its serial number, dates, the program, editing history, comments, and the thumbnails some cameras keep of the picture as it was before it was cropped. This covers photos (JPEG, PNG, WebP, GIF, HEIC and AVIF), videos (MP4, MOV, 3GP, WebM and MKV), and drawings (SVG), along with pictures inside a drawing. A video loses its tracks of timed metadata too, where some cameras record where they were at each moment, and anything a phone adds after a photo's end, such as a motion photo's video. Nothing is compressed again: what a photo or video shows stays as it was, byte for byte, and so do which way up it goes and its colors. A drawing keeps what's drawn, without what drawing programs keep for themselves, such as layer names and the paths of files on the sender's disk.

This is on unless someone turns it off on a device, in Privacy settings, which first says what files will then show and asks to be sure. Other files, such as documents, sound files and RAW photos, are sent as they are, and so is a file that doesn't read the way its kind should. What a picture shows can't be taken out, and nor can the faint pattern a camera's sensor leaves, which can tie photos to the camera that took them.

## Link previews

The sender's device makes a link's preview while they write: it fetches the page, and the title, description and a small picture travel encrypted inside the message. Recipients never contact the site, and the server never sees the link. The site sees the sender's IP address, as it would if they opened the link, and from when the link is typed, even if the message is never sent. Pages are fetched without cookies, only over HTTPS, and only from public addresses: redirects are checked one at a time, and names that lead to this machine or a private network are refused. What counts is where each connection really went, so a site's DNS can't switch where it points between the check and the fetch: the desktop app connects through a small proxy of its own, which reaches only the address it checked, and the iPhone and iPad app drops what it fetched if the system says it came from this device or a private network. When the system is set to use a proxy for a link, that proxy decides where the connection goes. Previews can be turned off on each device.

In the web app, the page can't fetch other sites, so its host, `zuna-web`, fetches pages for it by the same rules, and only on port 443. It checks the address a name leads to as it connects. The web app's host therefore sees which links are previewed, and sites see the host's address instead of the sender's. The chat server still never sees them. A host can turn previews off.

A preview's title and picture are the sender's claim about the page, like the message's text, so a card can say anything. The app only shows a preview for a whole link in the message's own text, always shows which site that link really goes to, and requires its picture to be inline: a preview can't make your device load anything.

## Shared locations

A shared location is where the sender's device said it was, sent inside the encrypted message like its text. The app only asks the system where it is when someone chooses to share it, and shows what it found before sending. Nothing in a message loads a map, since that would tell a map's server where people are looking: the app shows the coordinates, and only opening them, on OpenStreetMap from the desktop and the web app or in Maps on iPhone and iPad, tells that service.

## Forwarding

A forwarded message is a new message from whoever forwarded it. On the same server it names the original author, and its files aren't uploaded again: the copy refers to the same encrypted file, with the secret it was made with, which travels inside the message, so the server can tell that a file was forwarded, though not what's in it. The file stays until the last message using it is deleted. Forwarded to another server, a message only says it's forwarded, and its files are uploaded there again. The "forwarded from" label is the forwarder's claim, as in other messengers.

## Data on your device

Sensitive local data is encrypted with a device key held in your OS keychain (DPAPI, Keychain or Secret Service), each value naming the table and row it's in, so it can't be moved elsewhere. What decides whom to trust is sealed the same way: pins, verifications, how far along each person's chain of keys this device is, and when each device came and left each conversation. Chains are checked again from the pinned key each time the app starts. Something outside the app changing any of it gets a warning and the most careful reading. Rows taken out, or the whole database put back as it was, can't be told apart from what the device did itself. The search index stores keyed hashes of words instead of readable text, and the index of each message's photos, files and links, and of which ones mention you or reply to you, names their kinds the same way, though how many a message has is in the clear. If Linux has no keychain available, the app warns you in Settings, because this protection is weaker there, and seals the same key once one is. Started with the login, it waits up to 20 seconds for the keychain first.

Files are decrypted to disk only to be shown, played or saved. The desktop app keeps them in a `cache` folder in its data folder, with the voice and video messages it records and the pictures pasted into it, and empties that folder as it starts and as it quits. A voice or video message it recorded goes from there once it's been sent. iOS keeps its decrypted files in a folder of their own, emptied each time the core starts. The web app keeps them in memory.

The web app has no keychain to use, so its device key is in the browser's own storage, next to the data it protects. Anyone who can copy the browser's profile can read that data, and Settings says so.

On the iPhone and iPad, the share extension uses the same data and device key as the app, from the same Keychain group, and asks for Face ID or the passcode first when App lock is on. What it hands the app while the app is awake is sealed with a key from the device key. Files being shared wait in the App Group until they're sent, as readable as they were in the app they came from.

## The web app's host

- **The web app's host is never a chat server.** It runs as its own program, `zuna-web`, on an address of its own. A chat server, or someone who breaks into one, can't change the code, and its pages can't reach the web app's storage.
- **It loads nothing from anyone else.** Every file comes from its host, under its content security policy: no inline scripts, and images only from memory. The host also sends `frame-ancestors 'none'`, `X-Frame-Options`, `Cross-Origin-Opener-Policy` and `nosniff`, and pages it fetches for previews are marked so they can never run as pages there.
- **A copy can be checked.** Each release lists the SHA-256 of every file the web app serves, and `scripts/check-web.mjs` compares a running copy with it. This shows what the host serves when you check, not what it serves to everyone at every moment.

[WEB.md](WEB.md) says how to run it.

## The desktop app

The desktop app draws its own interface with GPUI, without a web engine, so nothing a message carries can run as code in it. What a message says is checked in the core (`validate.ts`) before anything shows it.
